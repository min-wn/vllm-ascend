# Down 通信边界：基于已有时间线的瓶颈分析

更新：2026-10-19。本轮不启动新的 NPU 实验。
只分析上一轮保存的六条完整模型 trace，并只读核查本机接口与源码。

后续更新（2026-10-20）：AIV GEMM/ReduceScatter 已完成当前机器上的 eager、ACLGraph 和闭合端点验证，
恢复完整输出后获得局部收益，见 [融合 Down 结果](aclgraph_fused_down_result_zh.md)。
下文接口未验证的表述保留为这份历史分析当时的状态。

## 已确认的结论

当前瓶颈应描述为 **Down 输出完整就绪之后，长时间执行 SDMA 通信任务，
计算主流同时等待归约完成**，而不是笼统的“多流调度不够好”。
最值得改变的是生产者与通信的整体屏障，或通信实现本身的数据移动路径。
本轮没有测出新的加速，不能把通信时长直接写成优化收益。

### 64 次 Down 后归约的细分

单位 ms。每行来自一个 rank 的独立时间线，不跨 rank 相加。

| step / B / token 容量 | rank | 归约总时长 | SDMA 任务 | 显式 Notify Wait | SDMA 占比 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 0 / 98 / 400 | 0 | 16.048 | 14.420 | 0.161 | 89.85% |
| 0 / 98 / 400 | 1 | 16.001 | 14.414 | 0.098 | 90.08% |
| 1 / 73 / 304 | 0 | 12.783 | 11.002 | 0.299 | 86.06% |
| 1 / 73 / 304 | 1 | 14.072 | 11.054 | 1.567 | 78.55% |
| 5 / 124 / 496 | 0 | 19.532 | 17.803 | 0.272 | 91.15% |
| 5 / 124 / 496 | 1 | 19.515 | 17.798 | 0.277 | 91.20% |

每次归约都有同一形态的 14 个子任务：
6 个 SDMA、4 个 Write Value、4 个 Notify Wait。
分析器核对时间包含关系、物理流、Task Id、Subtask Id 唯一性，
并拒绝不同任务混入或不同任务类别重叠后直接求和。
129 次归约全部覆盖，其中 embedding 单列，O/Down 按真实投影顺序映射。

Down 中两个长 SDMA 子任务（当前 trace 的索引 5、12）
占归约总时长约 75%～88%；其余四个 SDMA 较短。
这说明主要时间落在少数长任务，而不是几百个微小启动间隙。

**精确边界：** 导出的 trace 没有这些 SDMA 的字节数、源/目标地址或算法阶段名。
所以不能断言两个长任务分别是 ReduceScatter/AllGather，
也不能据此声称消除其中一个能将链路通信减半。
SDMA 时长可能包含内部等待，不等于已测得纯链路带宽。
Notify Wait 只是可见的显式等待，不代表系统所有等待。

### 已排除的错误优先级

- Down 算子结束到 collective 开始，64 层合计约 40～42 µs；
  collective 结束到同一计算流的下一 AI kernel，合计也约 41 µs。
  这一边界的可见调度空隙只有约 0.08 ms，无法承载多毫秒收益目标。
- 每步 Down 归约内部未被子任务覆盖的间隙合计约 1.26～1.31 ms，
  Write Value 合计约 0.18 ms。这些间隙不能全部归因于 CPU 启动。
- step1/rank1 的显式等待确实更高，需要保留为状态与跨 rank 节奏的诊断项；
  但另外五条 trace 的显式等待占 Down 归约约 0.6%～2.3%，
  不支持把“两卡同步偏差”当成普遍主因。
- 不能把主计算流中的 EVENT_WAIT 再加到 collective 时长上：
  它是在等待同一段通信结束，二者不是两份独立成本。
- 之前约 21 ms 的 GDN 提交大多已经被重叠，不能将其全部回收预算
  再与通信预算相加。

## 官方融合为何还没有进入当前对照

当前完整模型诊断通过权重加载器启用 eager 模型，
再用 `UpdatableGraph` 手工捕获，前向显式设置 `skip_compiled=True`。
它是 ACLGraph 回放，但没有经过官方 FX/编译融合 pass。

当前仓库的 `MatmulReduceScatterFusionPass` 匹配
`unquantized_gemm -> reduce_scatter`，还支持两种 padding 形态；
它不会将现有 `gemm -> all_reduce` 自动替换成融合 AllReduce。
注册门槛为 `fuse_gemm_comms` 和硬件能力；
A2 profile 包含该能力，标准设备包装默认使用 `comm_mode="aiv"`。
这些都是源码声明，不证明旧驱动上这个具体工作负载已可执行。

因此，“当前最快 Padding”应理解为
**此前已测控制组中最快的完整容量 Padding**，
不能理解为已覆盖全部官方融合路径的最强生产基线。
后续自研方案需要补齐相同边界的公开融合对照，才能避免虚假的切分归因。

### 本机接口核查

| 接口 | 能直接帮助什么 | 当前限制 |
| --- | --- | --- |
| `npu_mm_all_reduce_base` | 完整 GEMM 与归约内部流水，输出仍为复制布局 | 安装包文档明确写“增量场景不使能”；不能把 Q4 解码默认算作已支持。 |
| `npu_mm_reduce_scatter_base` | GEMM 与 ReduceScatter 内部流水；AIV 模式列有 A2 支持 | 输出归属改变；必须计入恢复完整输出或下游 AllGather 的成本。当前 ACLGraph/驱动资格未验证。 |
| `npu_all_gather_base_mm` | 输入收集与下一列并行投影重叠 | 安装包整体文档仍写训练场景；推理解码、图捕获、布局需要单独核实。 |

安装包说明中 `comm_turn` 只支持 0，
不能把它当成可随意调整的请求块粒度。
这些接口没有提供任意输出块的外部完成事件；
算子内部流水不等于另一个算子可安全读取其未完成输出。
文档中的“图模式”例子使用 torchair 编译，也不能替代手工 ACLGraph 的资格验证。
安装包文档的 PyTorch 版本列表明显较旧，故保留文档快照和适用性疑点，
不据此宣称接口绝对不可用，也不据导出符号宣称可用。

## 收敛后的实施顺序

### 先把一个 Down 边界的成本解释清楚

每个 rank 的真实 Down 输入为 [M, 8704]，
权重为 [5120, 8704] 的原 TP 分片，输出为 [M, 5120]。
M 取原有图容量，输入值和有效请求随 step 变化。
保持该矩阵形状、权重份数、BF16 和最终归约输出一致。

短期首选的资格对象是 **AIV GEMM+ReduceScatter，再恢复完整输出**，
因为仓库标准设备包装已明确选择这条模式，而融合 AllReduce 文档存在解码限制。
这只是适配优先级，不代表预计更快。
若恢复输出的成本吞掉融合收益，应直接收缩这一闭合边界方案。

对接口的最小核查只需回答：现有机器能否 eager 执行、能否捕获并重复回放、
结果与普通 Down+AllReduce 是否一致、时间线是否真的出现计算通信重叠。
不先扩大容量/模型/轮次矩阵，不修改驱动。

### 自研机制需要满足的条件

若公开融合仍留下可观的串行尾部，再考虑保持整块 GEMM 的输出块发布协议：

1. 图容量和缓冲区地址固定，每步输入仍允许变化；
   描述符记录实际请求、有效行和代号，不能用“相同容量”代替“同一批请求”。
2. 生产者完成某块全部 K 维累加并保证内存可见后，才能发布本 rank 就绪。
3. 通信同时满足对应 rank 的数据就绪与一致 collective 次序，
   完成归约后才发布下游可读状态；本地 GEMM 就绪不是全局结果就绪。
4. 重复回放必须处理代号换代和缓冲区生命周期，
   消费者不能占满资源等待一个无法运行的生产者。
5. 计入 GEMM 变慢、额外数据读写、同步以及最后一块排空时间。
   当前普通四块 HCCL 已测额外成本约 90 µs/边界，不能假定它消失。

这条候选的优化对象是“计算与通信之间的块依赖”，
不是把一次大 GEMM 重新拆成许多小 GEMM，也不是新增专用图容量。
第一块实际就绪时间仍没有测量证据，当前不能给出可信的端到端加速百分比。

## 与已有工作和毕设的关系

本轮贡献是可复算的瓶颈定位及对实验基线适用范围的修正。
GEMM/通信融合、块级通知、ReduceScatter 后保留行归属，
此前调研和已有官方算子均已涉及，不属于本项目首创。
它们也都是 Padding 可以使用的公共优化。

切分只有在进一步让不同请求块跨通信/下游边界合法提前推进，
并且超过使用相同融合能力的 Padding 时，才形成额外方法贡献。
若最终收益都来自公开融合，应如实按工程适配与实证分析表述，
不能包装成“切分独有的大收益算法”。

下一次优先补的是上述单边界的接口与时间线证据；
在此之前不启动完整模型流水大改，也不再扩展 sink/FFN 的独立微基准。
