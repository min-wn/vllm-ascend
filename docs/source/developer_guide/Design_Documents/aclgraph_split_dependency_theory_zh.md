# 请求切分并行的依赖与收益条件：理论分析及历史尝试核对

日期：2026-10-19。分析基线：仓库提交 `fdb9e9421`。

本轮只阅读已有源码、实验记录和 profiling 结论，没有运行新实验。
所有性能数字均为历史记录；公式是明确假设下的推导，不是新的性能预测。
本轮暂停融合算子资格试验，先回答：请求切分究竟增加什么调度能力，
以及此前失败的流水方案是否已经否定了当前候选。

## 1. 当前结论

切分独有的能力，是让某组请求在其他请求尚未完成时跨过算子、通信或层边界。
它增加可执行的独立任务，不减少模型必需的计算，也不自动增加硬件吞吐。
相对于保留整批依赖的 Padding，这种能力有意义；相对于已经具备同样请求块
依赖协议的单图实现，它不是多张图的专属优势。

**“不对称分组、有限领先、选择性合并”目前是一个需要筛选的调度问题，
不是已经找到收益的新算法。** 旧工作已经覆盖其中很多具体实例，
包括跨层推进、调整分支顺序、共享 GateUp、改变合并位置和按资源阶段调度。
不能把它们换一个名字重新当成创新。

仍值得理论推进的部分，是联合确定：在哪个边界切、让谁先走、允许走多远、
在哪个边界重新合并，并对每个选择核算最终汇合时间。
候选必须解释如何克服已测损失，而不只是产生更多时间线重叠。

## 3. 两个真实 decoder block 的依赖

以当前稠密 TP 模型的一层 FIA、下一层 GDN 为例，按请求组 X 表示。
Q4 的同一请求四个查询 token 保持在同组，不拆开其因果关系。
图中 Norm 包含相应的残差处理；具体实现仍同时传递 hidden 和 residual。

```text
第 l 层，FIA，请求组 X：
  输入 hidden/residual
    -> 输入残差/Norm -> QKV、Q/K 处理、RoPE
    -> 当前 K/V 写入 + 本组页表/真实长度就绪
    -> FIA -> gate/布局处理 -> 本 rank 的 O 部分和
    -> TP O 归约完成 -> 残差/Norm
    -> GateUp -> SwiGLU -> 本 rank 的 Down 部分和
    -> TP Down 归约完成
             |
             v
第 l+1 层，GDN，同一请求组 X：
  输入残差/Norm -> GDN 输入投影和布局处理
    -> Conv、门控、状态递推/solve -> gated Norm -> O 部分和
    -> TP O 归约完成 -> 残差/Norm
    -> GateUp -> SwiGLU -> Down 部分和 -> TP Down 归约完成

  GDN 状态支路：solve -> 必要的 accepted-state commit
                  -> 状态再次读取/工作区复用前完成，并在最终端点汇合
```

FIA 与 GDN 的中间核心不同，但都存在 O/Down 两类 TP 边界。
该图描述运算依赖，不声称每个框都对应一个独立可调度 kernel。
当前 compact GDN 的 producer/consumer 可能已经在同一个混合 kernel 中流水。

把 X 分别换成 A 和 B，可得到两条数学上独立的请求链。
依赖分为四类：

| 类型 | 必须保留什么 | 可以改变什么 |
| --- | --- | --- |
| 同请求数据依赖 | X 的下一层必须等 X 的前层输出；Norm 不能消费未经归约的 TP 部分和 | 不必因为 B 未完成而阻止 A。 |
| 同请求跨 rank 依赖 | A 的 O/Down 必须收齐所有 TP rank 对 A 的贡献 | 不要求 A、B 的归约输出同时被消费。 |
| 状态生命周期依赖 | KV 页写入、Conv/SSM 更新、候选状态提交、缓冲区使用各自有顺序 | 独立请求或独立层的状态可分离，但必须证明地址与生命周期安全。 |
| 实现引入的整批依赖 | full-M GEMM、整批 collective、共享临时区、单流提交都可能形成 join | 可以拆分或换接口，但拆分成本和资源顺序不能省略。 |

共享只读历史 KV 页不妨碍独立读取；可写页、状态索引、暂存区不能因请求分组而冲突。
本步跨层提前推进也不等于提前执行下一生成 step；下一 step 的 token/接受结果仍有真实依赖。

### 真实源码提供的边界

- `benchmarks/multi_graph_tp_gdn_phases.py` 的 `project/core/output` 已拆出输入投影、状态核心与 O 投影；`partition` 以 view 分组，残差一同分组。
- `benchmarks/multi_graph_tp_attention.py` 的 `finish_core_pipeline` 已在整批投影后切核心，并在整批 `prepare_mlp` 前合并；这就是已有的选择性合并实例。
- 同文件 `finish_adjacent` 在提交下一层 collective 前等待前层 Down B，保留双 rank 的共同通信顺序。删除该等待前必须重建完整顺序证明。
- `benchmarks/multi_graph_tp_gdn.py` 的 `prepare_mlp` 同时包含 post-Norm、GateUp 和激活；移动这个函数不等于只移动 Cube 工作。
- `benchmarks/multi_graph_gdn_q4_log_backend.py` 的 `reserve_exclusive_capacity` 明确要求共享 backend 的调用互斥，且提交完成后才能复用；`__call__` 拒绝尚有 `_pending_commit` 的再次进入。
- `benchmarks/multi_graph_gdn_q4_full_probe.py` 确实启用了上述互斥工作区，并在完整模型端点汇合所有 commit。旧多流适配器不能未经修改就套到当前 compact 完整模型上。

每层 backend 独立，不意味着所有层的 scratch 都相互冲突；这里的限制主要是
同一 backend 的分支重入、事务表示和复用协议。内部一次调用中的安全分块，
也不能等同于两个独立调用的安全并发。

## 4. 从原理上看，切分何时能赢

### 4.1 先区分两种作用

**生产提前：** Down A 完成后先归约 A，同时计算 Down B。
它不需要 A 跨层。这种流水可以由一个整批融合算子内部提供，属于公共优化。

**消费提前：** A 已归约后进入下一层，B 还在前层。
它需要跨算子或跨层的请求块完成协议。若 Padding 仍保留整批消费屏障，
它无法执行这一调度；若单图也实现该协议，它已经采用了相同的请求分块机制。

因此必须分别问：是否确实需要请求块依赖，以及是否确实需要多张图。
后者没有原理上的必然性。

### 4.2 单个 Down 边界的精确简化模型

设整批 Down 时间为 d，整批归约为 c。
切成 A、B 后分别耗时 dA、dB、cA、cB。
假设计算串行、通信串行，两类资源可无干扰重叠，输入已就绪，
两个 rank 的通信顺序一致且没有到达偏差，则：

```text
Padding: d -> c
Split:   dA -> [dB || cA] -> cB

T_padding = d + c
T_split   = dA + max(dB, cA) + cB

delta_D = dA + dB - d
delta_C = cA + cB - c
节省 = min(dB, cA) - delta_D - delta_C
```

这解释了为何“小组先行、大组在后”有时较好：更早启动首个归约，
再用较长的尾部计算隐藏它。但如果小组归约很短、或小 GEMM 极低效，
继续缩小 A 反而无益。要匹配的是时间，不是机械对半分请求数。

实际还需计入布局/汇合、update、资源干扰及 rank 偏差。
历史独立 Down 实验的正结果符合这一机制，但不证明跨层消费提前有额外收益。
当前普通通信两块比整块多约 29 µs 的小测，只约束当时独立通信端点，
不能直接当作每层完整模型的固定 delta_C。

### 4.3 “A 提前做下一阶段”要跨过多大的门槛

假设某个下游计算资源空闲，A、B 输入到达时刻为 rA <= rB。
该资源按 A 后 B 串行计算，分支时间为 eA、eB，整批时间为 eF。
暂时假设上游产生 rB 的过程不受这些计算影响，则：

```text
整批消费完成 = rB + eF
分支消费完成 = max(rB, rA + eA) + eB

收益 = min(rB - rA, eA) - (eA + eB - eF)
```

即：能利用的提前量，要大于把下游算子拆开的损失。
这也说明单个 A 更早完成不充分；必须观察 B 完成及最后 join 是否提前。

**实际 decoder 最容易违反的就是“rB 不变”。**
A 的下一层输入投影和 B 的 Down 都用 Cube，并可能竞争 HBM；
让 A 抢先会推迟 B 输出，进而推迟 B 归约及最终 join。
旧 wavefront 实验正好测到了这种竞争。不能拿原 Padding 时间线上的 rB
作为新调度中保持不变的输入，再声称得到净收益。

### 4.4 合并与不合并的真正取舍

- 立即回到 full-M 下一层投影：避免后续小 GEMM，但领先通常只能用于短 Norm 等工作；没有持续跨层窗口。
- 整段始终分开：更多跨层就绪任务，但反复支付输入投影、O、GateUp、Down 的碎片化，以及权重访存和额外归约成本。
- 只在一个有限段内分开：可以限制累计成本，但必须在该段最终汇合处赢。短段仍可能只有小收益，不能预设它兼得两端优点。

因此，“保留所有 full-M GEMM，同时任意跨层领先”不能由普通整算子接口实现。
前一层整批输出未齐，下一层普通整批 GEMM 就缺输入。
要同时保留大 GEMM 效率与分块消费，必须增加支持部分输入就绪的执行协议，
并证明权重复用仍有效；这已经是算子/运行时工程，也能被公平的 Padding 对照采用。

## 5. 当前最值得保留的理论候选

候选名称：**以最终汇合时间为目标的有限段请求流水**。
这里“有限”限制的是分支跨过的计算/TP 边界数量，不是固定请求内容或人为固定 batch。

### 5.1 决策对象

把相邻真实 decoder 层展开为任务图，候选联合选择：

1. 默认容量表允许的请求分组，以及先执行哪组。
2. 从哪个 producer/归约边界开始保持分支独立。
3. 哪些下游任务可以提前，哪些资源冲突阶段必须串行。
4. 在哪个昂贵投影前重新合并，或是否值得付费跨过它。
5. 两个 rank 一致的 collective 顺序，以及必需的状态/缓冲区汇合。

不预设小分支永远优先，也不预设固定领先一层最优。
通信队列有已就绪的 B 时，为等 A 的下一次归约而让队列空转必须付出代价。
同一 communicator 上不能由各 rank 独立选择下一个请求组。
加入计算流顺序、通信流顺序和内存复用边后，整张任务图必须无环。

### 5.2 先用“必须支付的额外工作”淘汰，而不是先想象理想重叠

对每个候选记录以下五项：

| 账目 | 需要回答的问题 |
| --- | --- |
| 新释放的工作 | 哪个原来不能执行的真实任务现在可以执行？它在何时得到完整输入？ |
| 最小切分代价 | 为释放它，最少必须拆开哪些 GEMM/归约？有没有依赖仍要求整批？ |
| 可用资源 | 释放时是否有可用 Cube/Vector/通信能力？提前执行会否推迟尾分支？ |
| 被替代的旧重叠 | 是否丢失 AR/core、commit/MLP 等原本已经存在的重叠？ |
| 汇合结算 | 加入所有布局、update、通信、提交和最终等待后，最晚分支能否更早结束？ |

当前可以确认通信是较大成本，却不能确认每个等待窗口都有足够独立工作。
三个旧完整模型 step 的 rank0 无 AI 重叠通信约 21～32 ms，是候选预算所在；
不是全都可回收。Down 边界前后可见启动空隙仅约 0.08 ms/step，
因此优化对象应是传输期间可做什么，而非继续微调主机启动间隙。

当前 ready-tile GDN 已改变计算阶段时长和资源需求，
旧约 500～1000 µs 的原生 recurrence 窗口不能作为现方案的独立 Vector 空闲预算。
不能一边使用新 GDN 的低延迟，一边保留旧 GDN 的长窗口预测更多重叠。

### 5.3 把“跨一层”收紧为一个具体候选

从第 l 层 Down 开始，考虑以下三个出口，且所有最终状态工作都要结算：

| 重新合并的位置 | 必须付出的切分 | 能获得的能力 | 当前判断 |
| --- | --- | --- | --- |
| 第 l+1 层输入投影前 | 前层 Down/归约，最多分支输入 Norm | 生产通信重叠，提前少量 Norm | 历史已有；不能称为持续跨层计算流水。 |
| 第 l+1 层 O 投影前 | 前层 Down/归约，下一层输入 Norm/投影和 attention/state core | A 可在 B 的前层归约期间提前生成下一层 attention 输入，并推进核心 | 是具体的有限段候选；下一层 O、GateUp、Down 可以恢复 full-M。 |
| 第 l+1 层 GateUp 后或更深 | 再切下一层 O/归约、Norm、GateUp，可能还有 Down | 更长的跨层独立链 | 与旧失败方案重合更多，累计成本更高，不应优先假设有收益。 |

中间一行相对于“所有层都拆”的差别很具体：
付出下一层输入投影的碎片化，在 O 前就合并，避免把下一层 GateUp 再拆小。
它与旧 shared-core 路线也不同：旧路线等完整输入投影结束才切 core，
没有通过拆输入投影获得这次跨层提前量。
在本轮核对的记录中，尚未找到这个精确出口、当前 compact 基线的闭合结果；
这只说明记录覆盖范围，不证明它有创新性或性能优势。

这个候选还有一个容易高估的上限。继续使用 4.2 的简化 Down 模型，
不允许下一层 A 输入 GEMM 与前层 Down B 争用 Cube：

```text
Down B 计算完成：dA + dB
A 归约完成：    rA = dA + cA
B 归约开始：    max(dA + dB, rA)
B 归约完成：    rB = max(dA + dB, rA) + cB

A 下一层输入 GEMM 最早开始：
  不早于 max(dA + dB, rA)，还需等待 A 的输入 Norm
```

所以在不抢占 Down B 的前提下，A 相对整批输入投影的启动提前量
**至多是最后一块 B 的归约时间 cB**，还不是所有前层通信加计算。
在同样的理想无干扰模型中，只看下一层投影完成处，新增节省至多为：

```text
min(cB, 下一层 A 投影时间)
  - (下一层两块投影总时间 - 下一层整批投影时间)
```

这是相对“相同前层 Down 流水、下一层完整投影”的局部比较，
不是相对原始 Padding 的完整两层收益。
下一层 core 可能增加或减少最终收益，需连同分支布局及提交一起分析。
当前 ready-tile GDN core 已含混合计算，不能再把它看作免费与 B 投影并行的纯 Vector 段。

这个推导给出新的筛选方式：**先问最后一块归约能否支付一次输入投影拆分，
而不是先提出多层流水再希望摊薄成本。**
若连这个局部门槛都过不了，需要新的算子消费协议或不同依赖边界；
继续加流、加层数并不能自动补救。
FIA 到 GDN、GDN 到 GDN 都适用这条前层 Down 推导，
但下一层投影/core 的实际代价和状态约束不同，不能共享一个收益估计。

### 5.4 如何定义一个可以比较的优化问题

以相同输入、输出布局、状态语义的完整汇合点作为段边界。
每个候选边从入口执行到出口，时间包括段内全部计算、通信与必须完成的状态工作。
全批执行也是候选。目标是减少整个路径的完成时间，而不是最大化重叠面积。

如果出口有统一的存储状态，且全部会影响下一段的异步工作已经完成，
可以将理论问题写成段选择：

```text
V[j] = min_i (V[i] + cost(i -> j, 某个合法调度))
```

这是建模方式，不是已实现算法，也不保证实际 cost 可准确预测。
若出口仍有 pending commit、不同布局或跨段通信，状态必须携带这些差异，
不能强行用上述简单递推；反过来，为简化模型新增全局同步也可能毁掉收益。

更粗的淘汰条件是资源工作量下界和依赖关键路径下界。
但 kernel 墙钟时长不是精确资源占用量，不能把 Cube/Vector 标签分别相加
就称为严格硬件下界。当前 trace 支持定位候选，尚不足以完成这种证明。

### 5.5 动态 batch 如何处理

每步已知的是当前 batch、真实长度、请求映射和页表；不需要未来输入值。
方案可在回放前从有限的已捕获模板中选取分组和调度，图内保留稳定地址与拓扑。
真实长度 update、H2D 和最终汇合仍执行。

普通 ACLGraph 不因这套理论而自动支持图内任意动态调度；
需要新设备调度器时，必须单列其实现与成本。
只复用默认容量，不为 B98 新造 49 或 98 的分支容量。
模板数量、捕获时间、scratch 容量、选择开销也都是方案成本。

请求重新分组应优先改变描述符或视图；如需要 gather/scatter，必须计时。
不复制额外 attention 权重，不把请求组改成 attention-head 图切分。

## 6. 与旧方案和已有工作的区别应该怎么写

| 内容 | 归因边界 |
| --- | --- |
| 微批、跨层流水、多流、计算通信重叠 | 都不是本课题可以直接声称首创的机制。 |
| 整批 GEMM 内部提前发布 tile、GEMM/通信融合 | 公共能力；Padding 必须得到相同能力。 |
| GDN ready-tile、compact state、延后 commit | 已实现的公共优化；先纳入对照。 |
| 不对称请求分组、共享 dense、选择性合并 | 我们以前已分别尝试；不能当作刚提出的新想法。 |
| 动态容量约束下联合选择切分、顺序、领先范围和汇合边界 | 可以进一步形式化的候选贡献；目前没有完成算法、收益证明或与外部工作的创新性比对。 |
| 多张图本身 | 不是贡献证明；同等请求依赖调度也可能放进一张图。 |

毕业设计若继续这条路线，更准确的问题是：
**在固定图容量下，怎样用最少的矩阵碎片化代价，释放能够缩短最终关键路径的请求并行。**
需要把调度机制、代价模型、动态选择与端到端证据连起来，
不能仅凭“支持多流”或“比串行切分快”成立。

本轮没有重新检索外部论文，不作“文献中尚未有人提出”的结论。
已有外部工作调研继续参考 [研究记录](aclgraph_dynamic_shape_research.md)；
后续创新性判断需针对最终形成的具体算法重新比对，而不是针对宽泛流水概念。

## 7. 下一步仍只做理论时，应完成什么

先完成一个具体闭合段的可行性分析，而非继续枚举更多多流变体：

1. 选取 FIA 到 GDN、GDN 到 GDN 两类边界，列出可提前任务和为此必需的切分算子。
2. 对每条候选路径补齐双 rank collective 顺序、状态事务和 scratch 生命周期；无法安全表达的路径先淘汰。
3. 在最新完整模型 trace 中定位对应原始区间，用旧负结果约束碎片化与干扰风险；不把旧算子时长当作新路径的测量值。
4. 为每个候选写出超过 Padding 所需的最低提前量，以及与现有公共融合对照的区别；预算不足即停止该候选。

本轮已经完成历史反证整理、依赖分类、两个简化收益公式和候选问题定义。
尚未完成最新基线下某个具体跨层调度的可信成本预测，
也未证明其能达到 5% 或其他端到端收益。
最有价值的下一结论应该是“这个具体依赖窗口足够/不足以支付这些必需成本”，
而不是再次说“理论上可以并行，所以可能更快”。


## 8. 用户批准小实验后的更新

上述第 7 节保留理论阶段的判断；随后已按用户“尝试一下”完成一次闭合段小实验。
当前 O 前合批方案，相同切分算术提前执行节省 141～165 微秒，但仍比 Padding 慢 2.72%～3.34%。
profile 确认输入 Norm/投影占用了最后一块归约窗口，core 开始时该归约已经结束。
因此下一候选是只拆输入投影、在 core 前合批；是否能够覆盖新增布局整理成本尚未验证。
本次没有新全模型收益，也不把这项机制直接称为原创算法。
实验范围、数值差异、profile 到达偏差与原始证据见
[有限领先小实验结果](aclgraph_bounded_lead_result_zh.md)。


## 9. core 前合批的小实验结果

随后实现只拆下一层输入投影、在 GDN core 前合批。
三轮同轮对照中设备时间比 Padding 减少 2.17%～2.43%，包括六次合批复制。
相同算术但不提前执行时仍慢于 Padding，支持消费者提前执行带来净收益的判断。
目前仅为合成上游输入的闭合段，不能外推全模型，也未建立原创算法结论。
完整条件、数值限制和下一步见 [core 前合批结果](aclgraph_core_join_result_zh.md)。
