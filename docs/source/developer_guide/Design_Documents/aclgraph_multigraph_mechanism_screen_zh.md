# 多张图能多做什么：机制审查与方案收紧

日期：2026-10-20。延续[第一阶段方案](aclgraph_multigraph_stage1_analysis_zh.md)。
本轮只复算已有动态轨迹、六条近期 trace，并阅读源码与原始文献；没有新 NPU 实验。

## 1. 本轮推进了什么

**目前仍没有足够依据进入大规模多图实现。** 新增的结论不是“并行不可能有用”，
而是进一步排除了三个容易误判的收益来源：

1. 在原 128 步轨迹上，最小合法双图容量仅比 Padding 少 **1.192%**；
   沿用最近融合契约时仍为 0%。不能把默认表的容量浪费当作大收益预算。
2. 该轨迹实际只用 17 个父容量。均分双图需要 34 个角色绑定模板；
   一个固定 256 主图加尾图的构造需要 17 个模板。不能拿所有理论容量对的数量，
   直接证明实际需要捕获大量组合或证明多图更省内存。
3. 当前 `q4_tile_solve_1` 是已经使用 Cube 生产者和 Vector 消费者的混合核。
   旧 Vector recurrent 路径的约 1 ms 窗口，不能当作新实现仍空闲的 Cube 时间。

此外，近期融合两层 trace 中约 0.5 ms 的“既无 AI kernel、也无 hcom”的区间，
几乎全部集中在 FIA 前的一个间隔；其余同类间隔合计约 14.6～19.1 μs。
这需要按更新供给和依赖等待分析，不能统称为许多可被事件调度回收的 kernel gap。
这些是 profiler 观察，不是无 profiler 端点收益，也没有证明该间隔全部由 host update 引起。

后续[完整路径核查](aclgraph_fia_update_critical_path_zh.md)已补齐同流轮询区间：
两层的大间隔约 98% 被 `MEM_WAIT_VALUE` 覆盖，但已有完整模型 B98、B73 共 12 条 trace 中，
16 次 FIA 前间隔合计仅 65.26～71.26 μs，全部图外事件写入早于首次 FIA。
因此局部等待不是当前已证实的完整模型大瓶颈，不能按层数相乘。
同一核查还找回六图互斥共享池的匹配源码；allocated 阶段增量约 27 MiB，
不能把理论组合数量直接换算成实际内存困难，也不能据此允许并发图复用同一池。

## 2. 将多图优势分成三个可以证伪的问题

### 2.1 独立请求是否释放了可用的并行工作

请求 A 可以在 B 未完成时前进，确实比整批屏障多一个自由度。
但必须同时存在可运行的后继、可用硬件资源，以及足够支付小矩阵、布局与同步的窗口。
近期融合切分已经实际测到“有重叠、最终更慢”，所以依赖独立只是必要条件。

在固定输入状态下，若 kernel、地址、流和依赖均相同，通常能把这次多图调度写成组合单图。
因此这种收益首先属于请求块依赖；是否需要独立 graph handle，要另做控制。
这里没有断言底层运行时对两种表达一定排出完全相同的时间线。

### 2.2 动态状态是否真的要求不同执行拓扑

先区分两种动态：长度、页表、请求身份、有效行变化，是数据或描述符变化；
是否执行另一个 kernel、采用不同子图顺序或分支数变化，才可能要求新的执行拓扑。
二者并不等价。一个固定拓扑的 kernel 可以读描述符后改变内部工作分配。

[FlashInfer 论文第 3.3 节及附录 D](https://arxiv.org/html/2501.01005v2)已用固定网格、
固定 workspace 地址与运行时计划表示 KV 分块、工作分配和部分结果合并，兼容 CUDA Graph。
这说明“长度组合很多”不足以推出“需要同样多的完整捕获图”。
其 GPU 实现不是本机可直接调用的基线，但公平比较必须允许单图采用同等动态描述符能力。

当前候选的真正前提应当是：**有值得使用、且当前单图数据接口不能低成本表达的执行选择。**
随后才比较捕获多个完整组合与复用独立模块的实际成本。
如果所有选择能由同一个既有 kernel 计划表达，优先把它作为公共优化处理。

### 2.3 有限捕获预算是否排除了有用的组合单图

这需要测出至少两个有用调度，再证明同预算缓存它们确实困难。
不能先枚举所有可能组合，再把大量从不使用或被支配的组合当作必须捕获的基线。
如果预算足够缓存全部实用组合，独立图的模块复用未必带来稳态延迟优势。
如果组合单图采用设备端计划、条件分支或合法的参数更新，还应继续缩小必须捕获的集合。

## 3. 原始动态轨迹的实际图目录

复算固定摘要 `0519bc80410b…` 的全部 128 步，不按性能挑选状态：
58 个实际 batch，使用 256、272、……、512 共 17 个默认容量；每个请求为 Q4。

| 构造 | 角色绑定图模板数 | 各模板容量之和 | 同时活动的最大输出行数 |
| --- | ---: | ---: | ---: |
| 每个父容量一张 Padding 图 | 17 | 6528 | 512 |
| 每个父容量均分为两 lane | 34 | 6528 | 512 |
| 固定容量 256 的主图，加默认容量尾图 | 17 | 2432 | 512 |

最后一行只是合法构造：父容量 C>256 时使用 `256+(C-256)`，C=256 时只用主图。
尾图为 16、32、……、256，全部来自默认表；它不是新的高效调度，也没有新性能证据。
均分构造中，同容量的两个并发 lane 使用各自资源实例，因此不能只数 17 个容量签名。

这些数字反而提醒我们：

- 多图可以降低“每个图单独保留全部容量”的行数总和，但这是特定分配假设下的代理。
- 若非并发图可以合法复用缓冲或内存池，Padding 也有这种机会。
- 同时活动输出行数没有减少；权重、激活生命周期、scratch、任务描述符、事件与状态暂存均未由此计数。
- 当前生产 wrapper 已通过 `get_global_graph_pool()` 接口取得图池；是否能安全复用、实际节省多少仍需运行时验证。
- 表中构造不穷尽所有模块设计，也没有证明这 17 个模板是全局最小值。

因此不能把 6528→2432 写成实际显存节省，更不能将其转写为推理加速。
实际逐步 Padding 容量合计 50688 token；允许最小合法双容量时为 50084，少 604 token。
与先前均匀枚举 65 个 batch 的 1.263% 不同，本轮 **1.192%** 按原始 128 步实际出现次数计权。
两者都不是时延上界；形状导致的 kernel 性能非线性仍须单独判断。

## 4. 为什么两条看似新的算子路线暂不成立

### 4.1 只切 KV，保持整批投影

这个想法可以避免拆小 QKV、O 与 MLP，但 KV 分块与稳定 softmax 合并已经存在。
除了 FlashInfer，已固定的官方 [PR #15336](https://github.com/vllm-project/vllm-ascend/pull/15336)
源码也有 `SplitCore`、FD 分块字段及合并消费者；这是源码事实，不是当前 legacy FIA 内部行为的测量。
本地[增量计划方案](aclgraph_incremental_attention_thesis.md)也已覆盖 selective KV splitting。

此前完整头策略与上游计划的正式 attention 链比较，均值改善约 1.79%，且有退化轮次与 P99 退化；
它不是独立多图的对照。把相同计划再装进几个 graph handle，不会自动消除合并和元数据开销。
若没有新的工作分配或资源理由，不重做“整批 dense＋两个普通 FIA 图”的旧负结果。

### 4.2 用另一张图的投影填满 GDN 的“Vector 阶段”

近期六条融合 trace 均将 `q4_tile_solve_1` 标为 `KERNEL_MIX_AIC`，耗时约 257～266 μs。
对应源码 `tile_pipeline_kernel.cpp` 中，Cube 生产者实际调用 `MatmulImpl::IterateAll`，
并用跨核信号与消费者形成流水。源码与 trace 标签共同约束了候选解释；
本轮没有重新建立旧二进制与每个 C++ 源文件的编译关联，也没有读取硬件利用率计数器。

因此，旧约 1 ms 的官方 recurrent core 与半批 GateUp 能并行的证据，
不能证明当前 compact 混合核也提供相同窗口。反过来，混合核标记也没有证明所有 Cube 一直满载。
没有新的内部阶段证据前，既不宣称有大窗口，也不宣称完全没有剩余空间。
要继续这条路线，应先回答混合核内何时产生真正可用的资源缺口，而不是增加原生流。

## 5. 新时间线核算：剩余通信与间隔不是同一个预算

以下来自融合两层已有 trace，单位 μs；不跨 rank 求和，不与正式计时混算。
通信列仅统计外部 hcom，不分解融合算子的内部通信。

| 模式/rank | 无 AI 重叠的外部通信 | 无 AI/hcom 区间 | 其中紧邻 FIA 前 | 其余无 AI/hcom 区间 |
| --- | ---: | ---: | ---: | ---: |
| 融合 Padding / 0 | 870.32 | 547.77 | 532.87 | 14.90 |
| 融合 Padding / 1 | 1119.78 | 499.04 | 484.44 | 14.60 |
| 融合提前切分 / 0 | 749.12 | 543.01 | 527.65 | 15.36 |
| 融合提前切分 / 1 | 758.56 | 511.74 | 495.78 | 15.96 |

这些通信仍是候选预算，但其输出依赖不能凭另一张图绕开；有些等待也可能包含 rank 到达差异。
无 AI/hcom 的区间可能有更新轮询、拷贝或其他设备任务，不等于设备全空闲。
特别是 FIA 前的单段等待，需要核对供给路径；单图本身已经支持 replay 与 task update 重叠。
即使该路径有优化，也要先提供给 Padding，不能自动归为独立多图贡献。

## 6. 一个更大但尚未合格的后备方向：跨设备请求流水

### 6.1 它改变的东西

如果当前同卡多流总受资源争用限制，可分析 PP2：将模型按层分到两卡，
不同完整请求组分别在两个 stage 上运行。每层权重只保留在所属 stage，
不新增完整注意力权重副本；它与此前复制 GDN 权重的 request-owner 方案不同。

```text
stage 0：前段层，图 A -> 图 B -> ……
                    |       |
                  hidden/residual 发送
                    |       |
stage 1：           后段 A -> 后段 B -> …… -> 本步全部结果与状态汇合
```

真正的结构机会是：两卡有物理独立的计算资源，且纯 PP stage 内不再需要逐层 TP 归约。
代价是更大的本地权重矩阵、较小请求组、流水线填充/排空、边界通信及 stage 不均衡。
同一 step 全部完成后才结束计时；不依赖下一生成 step 的未知 token 或接受率。

这不是“直接将现有 TP 图放到两卡上”，也不是已经找到的加速方案。
两卡 TP2 和两卡 PP2 都要使用各自适用的公共优化，改变并行策略的收益需要单列。

### 6.2 最小成本判据

设第 i 个请求组在两个 stage 的实际完整计算时间为 `a_i`、`b_i`，边界传输为 `c_i`。
在每 stage 计算串行、传输链路独立且可与计算无干扰重叠的简化模型中：

```text
A_i = A_(i-1) + a_i
C_i = max(A_i, C_(i-1)) + c_i
B_i = max(C_i, B_(i-1)) + b_i
T = B_last + 必需的最终汇合/输出恢复
```

这是指定三资源模型的递推，不是当前 NPU 的性能预测；真实共享带宽、发送缓冲复用与更新供给可能增加依赖。
若 K 个等时组、两 stage 完全均衡且忽略传输，单步仍有 `(K+1)/K` 的填充/排空因子。
K=2 即 1.5，K=4 即 1.25；减少归约不代表能免费拿走所有原 TP 通信时间。

已有 request-owner 的形状小测正好提示风险：相同 FLOPs 下，完整权重/半行的 GateUp
约 475 μs，对应 TP 形状约 317 μs；五投影独立输入 bundle 约多 261 μs。
这些是旧 GDN 局部资格结果，不能外推为 PP stage 时间，却足以否决“计算成本不变”的假设。
完整权重的 FIA、当前 compact GDN、多容量 stage 和 P2P 资格仍缺测。

只有按默认容量构成的组，在真实 stage 形状、当前公共融合和完整端点下仍有保守余量，
才值得做 PP 接入。若连忽略传输的筛选模型都无余量，就不开展模型重分片与缓存改造。
当前未过这个门槛，下一步不运行 PP 全模型。

### 6.3 图、状态和通信协议至少要满足什么

- 图模板固定所属 stage、容量和物理缓冲槽；切分保持完整 Q4 请求，尾部仍取默认容量。
- 权重按层驻留；KV、Conv、SSM 与候选状态始终由该层所属 stage 持有，不逐步迁移历史状态。
- hidden 与 residual 一并发送；请求 ID、位置、真实长度与行映射在两 stage 一致。
- 每条边使用固定票据 `(step, group, source_stage, destination_stage, capacity, dtype)`；
  发送与接收按共同计划提交，不能按各卡本地就绪顺序改变匹配。
- 发送完成前禁止覆盖源输出；接收缓冲在消费者和必要状态提交完成前禁止复用。
  必要的多个缓冲槽、事件与捕获实例全部计入资源预算。
- 当前 GDN backend 有互斥 workspace 和 pending commit 约束；按 stage 串行提交图，
  仍需证明异步提交已完成。不能仅因两组请求不同就重入同一个 backend。
- 旧 TP 多图协调器拒绝 parallel 的保护保留；PP 需要独立的通信与状态协议资格，不能删除保护冒充支持。

### 6.4 与已有工作及独立多图的关系

[FastPP，OSDI 2026](https://www.usenix.org/conference/osdi26/presentation/hwang)
已经研究动态 prefill chunk 和 decode 延迟调度以减轻 PP 不均衡，并报告特定 NVIDIA 配置胜过 TP。
[作者仓库](https://github.com/Sys-KU/FastPP)给出的启动示例关闭 CUDA Graph；
这不证明论文所有实验都关闭图，也不证明将其改成 ACLGraph 就有原创性。
官方 Ascend 也已有[动态 chunk PP](dynamic_chunked_pipeline_parallel.md)，主要面向 chunked prefill。

固定的 PP 微批次流水同样可以由各设备的组合图表达。
独立图的待研究增量仍是：默认容量下，有限模板如何支持变化的分组数、容量和 stage 进度，
在同预算组合图库之外获得净收益。不能将 PP 相对 TP 的改善全部写成多图图数优势。
这条后备线有更大的结构改变，却尚无足够证据和创新性依据升级为正式主线。

### 6.5 后续离线核算已完成，仍未通过实施门槛

[详细 PP2 账本](aclgraph_pp2_offline_screen_zh.md)确认：
默认 B98 的合法两组为 200+192，四组可取 104+96+96+96；
在零传输、计算效率相同的均衡模型中，单步跨度分别为原 TP 计算部分的 1.48、1.24 倍。
32/32 分层没有自然减少每卡长期状态空间；当前 compact kernel 与 Python 状态接口固定 TP2 头数，
纯 PP 所需 full-head 尚未适配。未用旧 BF16 core 或未融合 TP 通信量预测新收益。

历史 rank0 报告还保存了 68 图/17 bucket 的捕获记录，捕获阶段 allocated 差约 495.683 MiB。
这不是纯图内存测量，旧脚本 SHA 未完整恢复，也没有解决共享池与并发安全问题；
但它不支持先认定少量组合图无法驻留。PP 保留为后备，本轮未启动新 NPU 实验或全模型改造。

## 7. 下一阶段的明确顺序

1. **先补机制证据，不扩大原负结果。** 只接纳能指出新执行选择、新资源窗口或真实预算约束的候选。
   当前普通双 FIA、旧 Vector/GateUp 配对和基于理论组合数的路由器不进入实现。
2. 对现有 TP 主线，需先找到至少一个强基线下的净胜状态，再讨论多状态动态选择；
   对预算优势，先核实有用组合数、合法池复用与实际驻留资源。
3. 后备 PP 先做离线形状/内存/依赖账本；不通过计算效率与填充成本门槛就停止。
   缺少关键形状成本时，至多安排一个能够直接决定是否继续的小 profile，不先改完整模型。
4. 任何候选通过筛选后，沿用第一阶段的四对照、真实 update、完整状态端点和同预算动态轨迹协议。
   公共融合继续独立归因；先汇报完整候选，再深入实现。

**现阶段的成果是收紧了可行性判断；尚未形成可信的多图大收益算法。**
后备方向不是承诺，失败证据也不等于证明所有多图方案都无效。
