# FIA 更新等待是否是完整模型瓶颈：历史时间线核查

日期：2026-10-20。仅重读已有 profiling、原始报告及归档源码，未运行新的 NPU 实验。

## 1. 结论与研究含义

**两层探针中约 0.5 ms 的 FIA 前等待，没有在本次可用的完整模型时间线中重现。**
完整模型 B98、B73 的 12 条 trace，每条含 16 次 FIA；其同流前驱结束至 FIA 启动的
间隔合计为 65.26～71.26 μs，最大单次为 4.96 μs。
每条 trace 的 16 次图外事件写入均在首次设备 FIA 启动前完成。

因此不能把局部探针的等待乘以 16，也不能据此认定增加 host 更新线程或交错更新
会给完整模型带来数毫秒收益。当前证据只是否决了这个外推，
没有证明未来融合版完整模型、所有动态状态或其他运行栈都不存在更新等待。

同时，已找回调用源码的完整模型报告表明：互斥执行的多张完整图确实请求共享图池，
六张图捕获阶段的 allocated 增量约 27 MiB。不能未经核算，就把组合单图的图资源开销
当成必须采用独立多图的理由。这也不证明并发图能安全共用同一池。

这两项结果用于收紧[多图研究主线](aclgraph_multigraph_exclusive_plan_zh.md)：
后续需寻找真实未被覆盖的通信、依赖或硬件资源窗口，或证明有限资源下有用的动态组合价值。
本次没有新增多图加速结论，尚无已通过大收益门槛的方案。

## 2. 样本、计时与归因方法

| 历史运行目录 | 工作范围 | 样本 |
| --- | --- | --- |
| `two-layer-fused-v1` | 真实 FIA→GDN 两层融合探针 | 三种融合方案、两个 rank，共 6 条 trace |
| `full-core-join-v3` | 完整 64 层 decoder 与末尾 Norm，B98/Q4 | 三种方案、两个 rank，共 6 条 trace |
| `full-core-join-v4-profile` | 同类完整模型路径，B73/Q4 | 三种方案、两个 rank，共 6 条 trace |

三次历史运行均设置 `TASK_QUEUE_ENABLE=0`。每个方案、每个状态回放一张组合图，
不同方案分别计时；这里不是独立多图并发实验。
完整模型样本不是已接入全部公共通信融合的新版本。

对每次设备 `FusedInferAttentionScore`，找到同流前一个真实 AI kernel，
本次全部是 `ScatterPaKvCache`。统计前驱结束至 FIA 启动的间隔；
将同流 `MEM_WAIT_VALUE` 区间裁剪到该间隔，再取区间并集，避免重叠计数。
原始时间可能为字符串，计算使用 `Decimal`，不做跨 rank 时间戳相减。

另统计 CPU `npu::npu_fused_infer_attention_score` 调用和图外 `MEM_WRITE_VALUE`，
后者由 `Model Id == 4294967295` 识别。依据调用源码、数量及捕获层顺序关联，
trace 不导出事件目标地址，所以不能声称逐个地址匹配了更新任务与事件写入。

## 3. 两层探针：大间隔确实主要是轮询等待

单位均为 μs，每条 trace 含一次 FIA。

| 方案 / rank | FIA 前间隔 | 轮询区间并集 | CPU FIA 调用 |
| --- | ---: | ---: | ---: |
| fused_padding / 0 | 532.871 | 523.010 | 492.97 |
| fused_padding / 1 | 484.440 | 474.020 | 415.34 |
| fused_split_barrier / 0 | 567.832 | 556.591 | 454.90 |
| fused_split_barrier / 1 | 569.240 | 560.880 | 469.91 |
| fused_split_early / 0 | 527.650 | 517.070 | 457.07 |
| fused_split_early / 1 | 495.780 | 487.460 | 427.42 |

轮询覆盖间隔的 97.849%～98.531%。图外事件写入在 FIA 启动前约 3.9～5.1 μs 完成；
CPU 外层调用则提前约 60～65 μs 返回。CPU 调用与设备等待重叠，二者不能相加。
Padding rank0 的间隔包含 199 个 `MEM_WAIT_VALUE` 区间，对应同一根任务。

结合 `UpdatableGraph` 的等待、更新、事件记录协议，时间关系支持“等待更新供给”的解释。
它没有把整段时间进一步分解成纯 host tiling、运行时调度或 profiler 开销，
更没有证明可以无成本回收整个间隔。

## 4. 完整模型：已有前缀工作覆盖了更新供给

下表列出 Padding，三种方案的全部记录保存在原始复算文件中。

| 运行 / rank | 16 次间隔合计 μs | 最大单次 μs | 轮询并集合计 μs | 最后图外写入早于首次 FIA μs |
| --- | ---: | ---: | ---: | ---: |
| v3，B98 / 0 | 67.938 | 4.520 | 27.701 | 5519.650 |
| v3，B98 / 1 | 65.260 | 4.560 | 26.320 | 489.400 |
| v4，B73 / 0 | 69.283 | 4.741 | 28.441 | 11568.051 |
| v4，B73 / 1 | 68.900 | 4.640 | 28.960 | 459.540 |

全部 12 条完整模型 trace 中：

- 16 次同流间隔合计 65.26～71.26 μs；轮询并集合计约 26.32～29.94 μs。
- 全部 16 次图外事件写入早于首次设备 FIA；最后一次提前 318.247～11568.051 μs。
- 每条 trace 均有 16 次 CPU FIA 调用、16 次图外写入和 16 次设备 FIA。

完整图在第一次 FIA 前已有三层 GDN 工作，host 更新可与这些计算重叠。
现有非 ENPU replay 路径也已经先启动图、再提交更新，并非等待所有更新完成才运行图。
因此局部两层探针暴露的大等待，在完整模型里已有覆盖机会。

这里的间隔总和不是可回收时间上界，也不是反事实加速预测。
profiler 会改变 host 开销和 rank 间相对节奏；跨 trace 的提前量不能相减推导收益。
结论限于这些已有样本，后续若大改前缀计算或通信融合，应按新关键路径重新判断。

## 5. 图资源：找回调用源码后的证据边界

v3、v4 的四份 rank 报告均记录：默认容量 304、400，三种方案，共六张图。

| 捕获阶段计数 | 字节 |
| --- | ---: |
| 捕获前 allocated | 45,797,027,328 |
| 捕获后 allocated | 45,825,337,856 |
| allocated 阶段增量 | 28,310,528，约 27 MiB |
| reserved 阶段增量 | 654,311,424，即 624 MiB |

找回的 `multi_graph_gdn_q4_full_probe.py` 与各自 `launch.json` 中的 SHA 完全一致：

- v3：`ff7e80b46d7b6974547544e8c8aa5995e2367d8d0649a73fa83a6d0b9fab4269`。
- v4：`2b7fa5dcd4a207d8e28773eb6d457e6671efe7d11a91d2b275937359717d6e05`。

调用方显式创建一次 `torch.npu.graph_pool_handle()`，各次捕获传入相同的
`pool=pool, stream=root`，并明确说明这些图互斥执行。
这比[PP2 账本](aclgraph_pp2_offline_screen_zh.md)引用的 68 图历史记录多了匹配源码证据；
68 图版本的完整匹配源码仍未找回，不能把两次运行合并为一组资源测量。

这些计数包含该阶段发生的分配，不是纯图元数据或每图固定字节数。
不能线性外推全部动态状态的资源，也不能证明任意组合都放得下。
互斥图的池共享不能直接移植给并发图；并发时仍需核实 writable buffer、scratch、
KV/GDN 状态、事件、生命周期及 allocator 的合法复用条件。

## 6. 对后续方案的筛选条件

1. 不以“两层等待约 0.5 ms × 16”申请完整模型更新线程改造；已有并行 host 更新工作也不能重复命名为新方案。
2. 若提出多图可以掩盖更新，应指出当前完整路径上实际未覆盖的哪次更新、前后依赖及可执行的独立工作。
3. 若提出组合单图过多，应先给出有净收益的执行选择、实际常用组合及实际资源账本。
4. 公共 kernel、通算融合和更新优化也提供给 Padding；其收益单独归因。
5. 优先解释如何在保留大矩阵效率的同时释放请求间依赖，且不读取未完成输出。
   能否实现真正的局部发布、可用计算资源是否存在，仍需源码和接口依据。
6. 深入实现前仍需完整中文方案，以及 Padding、多图串行、多图并行、同依赖组合单图的最小验证计划。
