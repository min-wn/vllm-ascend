# 跨设备请求流水能否成为多图主线：离线成本核算

日期：2026-10-20。延续[多图机制审查](aclgraph_multigraph_mechanism_screen_zh.md)与
[第一阶段方案](aclgraph_multigraph_stage1_analysis_zh.md)。

**结论：跨设备 PP2 有减少逐层 TP 通信的结构机会，但目前未达到深入实现门槛，
也没有证明独立多图带来额外收益。** 本轮完成了默认容量分组、真实权重形状、状态内存、
单步流水条件和接入缺口的账本，没有运行新 NPU 性能实验。

这里的 PP2 是把前后两段层分别放在两卡上，让不同完整请求组在两卡交错前进。
它不新增模型权重副本，但改变了模型并行方式。它相对 TP2 的任何收益都必须与图数量贡献分开。

## 1. 依据与核算边界

- 使用既有 128 步动态轨迹，固定摘要 `0519bc80410b…`，全部步骤计入，不能按结果挑 batch。
- 每个请求完整保留 Q4；使用既有报告中的默认捕获容量，不新增专用容量。
- 模型仍为本机 Qwen3.5-27B：64 层，48 层 GDN、16 层 FIA，隐藏宽度 5120。
- 通过 SSH 重新读取模型配置、索引和 safetensors 文件头，共读取 149,632 字节文件头，
  没有读取张量数据、加载模型或执行 NPU kernel。配置、索引及 11 个文件头哈希与原库存一致。
- 逐层库存确认：每层 GDN 权重 766,546,720 字节，FIA 权重 744,510,464 字节；
  embedding 和未绑定的 LM head 各 2,542,796,800 字节。最后 Norm 为 10,240 字节。

历史完整模型探针的端点是 **64 层 decoder 加最终 Norm**，不包含 LM head 或完整服务请求。
本账本把 embedding/LM head 计入可能的驻留权重；另列全 Q4 logits 的计算不均衡情形，
不把历史 decoder 测量升级为完整生成时延。

## 2. 分组以后，单步流水仍然需要填充和排空

设强 TP2 Padding 的端点由计算部分 `P` 和可消除的暴露通信部分 `H` 构成。
先建立一个非常有利于 PP 的筛选情形：

1. 两个 stage 的计算工作均衡，时间与捕获 token 行数线性成正比；
2. PP 和 TP 的相同计算量具有相同有效效率；
3. 完全忽略 P2P、长度更新、H2D、额外提交、状态提交和最终恢复成本；
4. 本 step 所有组完成后结束，不用下一生成步、暂缓请求或未知 token 填满流水。

若父容量为 `C`、各组容量为 `c_i`，两 stage 均衡的单步跨度为：

```text
S = (sum(c_i) + max(c_i)) / C
T_PP = S * P
T_TP = P + H

PP 在这个情形下获胜，要求 H / (P + H) > 1 - 1/S。
```

`S` 是假定计算效率下的归一化跨度，**不是实际时间、实测收益或对任意算子的普适下界**。
长度异质性、kernel 形状和实际效率会改变它。FIA 更新等非通信成本不能无依据地并入可消除的 `H`。

### B98 的具体含义

动态程序穷举合法的正整数请求分组，在上述模型中最小化 `sum(c_i)+max(c_i)`；
相同成本时再选择更均衡的分组。以下所有容量来自默认目录：

| 请求组数 | 请求数分组 | 捕获容量 | 归一化计算跨度 S | 相同效率时所需可消除通信占比 |
| --- | --- | --- | ---: | ---: |
| 2 | 50+48 | 200+192 | 1.48 | 大于 32.43% |
| 4 | 26+24+24+24 | 104+96+96+96 | 1.24 | 大于 19.35% |
| 8 | 14+12+12+12+12+12+12+12 | 56+48+48+48+48+48+48+48 | 1.12 | 大于 10.71% |

基线是默认容量 400。49 个请求需要 196 行，默认目录应取 200；
这里没有新增“196 行图”或“49 请求图”。两组的 200+192 来自 50 个与 48 个完整请求。

这些通信占比只是计算效率相同、额外成本为零时的条件。
若用系数 `α` 表示 PP 的计算时间比上述理想值增加，条件改成 `1-1/(α*S)`。
例如 `α=1.25` 时，两组、四组、八组分别需要大于 **45.95%、35.48%、28.57%**。
这是一张敏感性表，不能把旧实验的投影比值当作所有层、所有容量的 `α`。

### 原轨迹的所有步骤

| 组数 | 按父容量计权的理想跨度 | 近似等请求数分组的跨度 | 模型最优分组容量削减 |
| --- | ---: | ---: | ---: |
| 2 | 1.49053 | 1.49511 | 0.947% |
| 4 | 1.24527 | 1.26073 | 0.947% |
| 8 | 1.12208 | 1.16035 | 1.065% |

计权方式是先求各步容量跨度之和，再除以父容量总和，不是实测时延均值。
八组的理想解有 15 步出现最大/最小组请求数大于 2 的情况，可能包含很小的尾组。
因此保留它只为展示理想模型，不把这种分组直接当作可靠调度策略；较均衡构造另列。
真实 FIA 的组代价还与序列长度有关，当前动态程序没有建立这种时间模型。

## 3. 降低流水气泡的代价：矩阵更小、完整权重反复使用

下面只比较线性投影形状，用 `[M,N,K]` 表示 `X[M,K] @ W[N,K]^T`。
PP 表内为每种分组中的最大组，其余组形状见原始账本。

| 投影 | TP2 / 400 行 | PP2 / 两组最大 200 行 | PP2 / 四组最大 104 行 | PP2 / 八组最大 56 行 |
| --- | --- | --- | --- | --- |
| GDN QKVZ | [400,8192,5120] | [200,16384,5120] | [104,16384,5120] | [56,16384,5120] |
| FIA Qgate/K/V | [400,7168,5120] | [200,14336,5120] | [104,14336,5120] | [56,14336,5120] |
| GateUp | [400,17408,5120] | [200,34816,5120] | [104,34816,5120] | [56,34816,5120] |
| Down | [400,5120,8704] | [200,5120,17408] | [104,5120,17408] | [56,5120,17408] |

PP 每卡持有一半层，但每层使用完整权重；近似相同总行数时，每卡总投影 FLOPs 与 TP2 相近。
它没有免费减少计算量。分组变多主要缩小流水气泡，同时把计算拆成更多小 M 的完整宽度矩阵。

仅以 BF16 权重字节为分母，GEMM 的 `2*M*N*K / (2*N*K) = M`。
因此这部分算术强度随 M 减小。按“每个组完整走过本 stage 所有层”的顺序执行时，
同一 stage 权重会被使用 K 遍；如果这些权重无法跨组保留在缓存，权重读取压力会随组数增加。
这不是已经测得的 HBM 流量；也不假设 kernel 的缓存、NZ 和公共融合行为完全相同。

旧真实 GDN 层的五投影 bundle 已观察到完整权重/半行形状比 TP 形状慢，
但它使用冻结的独立投影输入。旧 recurrent core 还是 BF16 materialized state，
并非当前 compact FP32 混合核。两者都不能拼成新 PP stage 时间或线性乘以层数。

**两组保留较大的 M，却要支付较高单步气泡；八组降低气泡，却显著缩小 M。**
当前尚无跨过这个权衡的真实形状成本证据。

## 4. 内存：32/32 分层没有自然获得更多状态空间

以下只做直接分配的 compact 状态算术，假设它能够推广到完整头数，
不代表当前代码支持 PP，也不证明实际 allocator 可以分配成功。

32/32 切分时，每 stage 都有 24 层 GDN、8 层 FIA。
TP2 是 48 层 GDN 的半头状态，PP2 是 24 层 GDN 的全头状态，乘积相同。
FIA KV 同理，历史状态仍要覆盖全部 128 个稳定 owner，不能按当前微批请求数缩减。

| 每卡项目 | stage 0 字节 | stage 1 字节 |
| --- | ---: | ---: |
| Decoder 权重 | 24,353,204,992 | 24,353,204,992 |
| embedding 或 head/最终 Norm | 2,542,796,800 | 2,542,807,040 |
| Compact FP32 base | 9,739,173,888 | 9,739,173,888 |
| Q4 Conv 候选状态 | 1,512,898,560 | 1,512,898,560 |
| 两套 log/valid bank | 1,264,951,296 | 1,264,951,296 |
| FIA 最大保留 KV | 5,423,235,072 | 5,423,235,072 |
| 小计 | 44,836,260,608 | 44,836,270,848 |

小计约 41.757 GiB/卡，尚未包含 products、投影与激活、边界多缓冲、图资源、通信 workspace、
权重格式副本、加载峰值、runtime 保留和碎片；未计 MTP/视觉权重，实际 loader 是否卸载也需核实。
以 64 GiB 做容量假设仅用于账本，不是当前空闲内存测量。

还核对了 null page：`reserve_owner_pages()` 从 page 1 分配 owner，实际需要 **1293 页**。
旧库存中的 1292 是 owner 页数；其 FIA 字节公式已经加 1，并不存在少算一页的字节错误。

28/36、30/34、31/33 等层切分也已计算，结果保留在 `audit.json`。
32/32 的 decoder 投影 FLOPs 均衡；若每个 Q4 token 都增加完整 LM head，
stage 1 相对平均计算量会多约 4.96%，34/30 的投影 FLOPs 更均衡。
这不是确定应选 34/30：FIA、GDN、Norm、采样和 logits 行选择的实际时间尚未计入。

## 5. 真正需要改的接口与生命周期

目前不能通过设置 `pipeline_parallel_size=2` 完成接入。

| 现有约束 | PP2 所需能力 | 不能采取的捷径 |
| --- | --- | --- |
| 原生混合核固定 8 个 key heads、24 个 value heads | 每层全头为 16/48，需要重新核算 tiling、并行任务、workspace 与精度 | 用旧 BF16 full-head core 的时间代替当前 FP32 核 |
| `Q4LogState.from_base()` 固定 [owners+1,24,128,128]，logs/valid 同样固定头数 | 全头状态、两套日志和 products 的一致几何 | 只放大 Python 张量而不改 native 索引 |
| `allocate_full_caches()` 要求 TP2、全 64 层、FIA 2 个 KV heads | 按 stage 持有部分层、FIA 全 4 个 KV heads | 沿用 TP2 cache 当作 PP 数据 |
| loader 要求 world size=TP=2 | PP worker 和按层加载/恢复真实权重 | 删除检查后假装已经支持 |
| backend 共享 exclusive workspace，并有 pending commit | 每 stage 顺序执行；前一使用结束后才复用 scratch，必要提交先 join | 因请求不同就重入同一 backend |
| `prepare_step`/`finish_step` 管理一次全局 step 事务 | 外层一次准备所有本步 owner；记录各组覆盖，全部提交完成后只 finish 一次 | 对同一 state 反复 prepare/finish 相同 step，或递增伪造生成步 |
| TP 协调器只同意 serial lane | PP 独立 P2P 协议与完整汇合资格 | 删除 collective 次序保护 |

完整 step 的拟定执行协议为：

1. 先冻结组计划与原始请求行映射，两 stage 对同一份计划达成一致。
2. 所有层的 KV、Conv、SSM 由所属 stage 长期持有；请求换组不迁移历史状态。
3. stage 0 顺序提交各组。输入 tokens、位置、真实长度和 accepted 状态按原请求 ID 对应。
4. 每组前段完成后发送 hidden 和 residual；stage 1 收到对应票据后才消费。
5. 通信票据至少包含 `(step, group, source, destination, capacity, dtype, tensor_kind)`。
   两端按共同计划提交 hidden/residual，不能按各自本地就绪顺序改变匹配。
6. 发送完成前保留源输出，接收后的消费者完成前保留目的缓冲。
   缓冲复用还必须等待相应 workspace 与状态提交完成。
7. 全部组结束后恢复本步输出行顺序，核对 owner 恰好执行一次、状态恰好推进一次，
   完成两卡最终汇合后结束计时。

B98 的三种分组捕获容量合计都是 392，hidden+residual 的边界数据为 **8,028,160 字节/step**，
只算 BF16 两个张量；未包含元数据、打包、额外复制和最终输出传送。
若使用两个最大组缓冲槽，源端和目的端都要保留各自槽位与事件；不能拿总传输量当缓冲占用。

每个 stage 每组一张图时，跨两 stage 的 replay 数为 4、8、16。
逻辑 FIA 参数更新节点数则为 32、64、128；TP2 两 rank 的对应数量为 32。
实际主机 API 可以批量提交，节点数不等于 API 调用数或更新时间，但增多的更新工作不能省略。

## 6. 图资源预算的新约束：历史上已捕获过 68 张完整图

重新审查已保存的 `q4-tile-full-replay-v8-queue0.rank0.json`：

- 同一原始轨迹，17 个默认 bucket，共报告捕获 **68 张图**；
- `compact_decode_transition` 分配 45,797,027,328 字节；
- `all_required_default_graphs_captured` 分配 46,316,788,224 字节；
- 两阶段分配差 519,760,896 字节，约 **495.683 MiB**；reserved 差约 **868 MiB**；
- 该轮动态试验结束时 reserved 为 48,012,197,888 字节。

这是历史 rank 0 的记录，状态注明完整正确性审计待完成；不借它新增正确性或性能结论。
阶段差同时包含预热、workspace 等变化，不是 68 张图的纯内存成本；
runtime 在 PyTorch 之外的分配和各 mode 的增量没有分解。
报告声明的旧 probe SHA 未在当前文件及该路径可见 Git 历史中找到完整匹配，
因此本轮只引用报告中的捕获数量和阶段统计，不归因于当前源码的具体池策略。

**它至少不支持“17 个默认容量的完整组合图显然放不下”的假设。**
独立模板可能仍有资源价值，但需要核实实际有用组合、共享池安全性和受限的具体资源。
不能靠理论组合数或各模板容量之和先认定存在资源瓶颈。

## 7. 与已有工作的区别：目前哪些还不能作为毕业设计贡献

[FastPP 原论文，OSDI 2026](https://www.usenix.org/system/files/osdi26-hwang.pdf)
研究动态 prefill chunk 和 decode delay scheduling，以减轻跨 stage 不均衡。
其 decode 策略会暂缓部分请求，待其他请求完成后恢复；论文使用 NVIDIA/SGLang 服务指标。
这些结果不能直接证明“当前 step 所有 Q4 请求必须完成”的时延会改善。
[作者仓库](https://github.com/Sys-KU/FastPP)的启动示例关闭 CUDA Graph，
不等于论文全部实验都关闭图，也不说明添加 ACLGraph 就是新方法。

[官方 Ascend 动态 chunk PP](dynamic_chunked_pipeline_parallel.md)已有 profiling、
chunk 预测和在线校准，明确要求 PP 与 chunked prefill。
本课题的闭合 Q4 step 不能直接借用其 prefill 目标函数。

| 机制 | 归因 |
| --- | --- |
| 按层 PP 减少 TP 归约 | 模型并行方式改变，已有工作 |
| 固定微批次流水、跨设备多流与 P2P | 已有流水机制，组合单图也能表达 |
| 用现有公共融合改善投影或通信 | 必须提供给 Padding，不是独立多图贡献 |
| 默认容量下动态重组少量模块图 | 条件候选；需先证明有用调度确实随状态变化、资源预算实际受限 |
| 本轮分组 DP、内存与阈值账本 | 可复算的筛选工具与约束整理，没有据此证明新的加速算法 |

固定 PP 流水在每台设备上仍可表示为组合 DAG。
独立多图若要成为贡献，必须额外证明：变化的组数、容量或进度产生可用选择，
同预算组合图库不能同样低成本覆盖，且独立提交的成本小于适应性收益。
本轮没有满足这些条件，因此不把 PP 接入包装成已经成立的毕设主线。

## 8. 决策与最小验证顺序

**本轮决策：PP2 保留为后备，不进入完整模型重分片和内核推广。**
原因是当前缺少有效计算效率、真实 stage 时间、P2P 资格和独立图增量证据，
并非证明 PP 一定比 TP 慢；没有用不同时期数据拼接一个虚假的负收益预测。

接下来优先从已有完整模型记录核实实际图资源与关键路径预算，
寻找至少一个在强 Padding 之上能获胜的执行选择，再讨论动态组合。
若没有有用选择，继续增加路由、图库或队列不会产生已知收益。

若后续证据重新使 PP 合格，最小实验按以下门槛推进：

| 顺序 | 内容 | 能决定什么 | 停止条件 |
| --- | --- | --- | --- |
| 1 | 复用当前版本记录确认强基线的可消除通信与不可消除更新成本 | 是否存在足够预算；不沿用旧未融合通信量 | 同条件下连乐观模型也无余量 |
| 2 | 只测能决定结论的完整宽度投影形状，优先两组、四组；不先接全模型 | 小 M / 全宽代价是否抵消通信预算 | 完整预算无保守净余量 |
| 3 | 仅在前两项通过后，资格验证 full-head compact、单边界 P2P 与状态协议 | 当前驱动与接口是否可执行、可捕获、可正确复用 | 任一关键资格失败 |
| 4 | 固定一段最小连通 stage，使用相同输入与更新协议比较四对照 | 收益来自流水还是独立 graph handle | 相同依赖组合图已取得全部收益，且无实际捕获预算优势 |
| 5 | 前述结果形成完整方案后先汇报，再考虑动态轨迹和完整模型 | 是否值得深入实施 | 不预先承诺升级 |

四对照是同等优化 Padding、多图串行、多图并行，以及相同分段/依赖的组合单图。
跨并行方式时另列 TP2 与 PP2：不能把“PP 比 TP 好”和“独立多图比组合单图好”合为一个百分比。
所有条件都计入真实长度更新、搬运、发送接收、状态提交与最终汇合。

## 9. 复现与验证

证据目录：`benchmarks/results/multi_graph_structural/pp2-offline-v1/`。

```bash
# 已保存文件头库存后，下面两步完全在 CPU 上执行。
python benchmarks/results/multi_graph_structural/pp2-offline-v1/audit.py
python benchmarks/results/multi_graph_structural/pp2-offline-v1/verify.py
```

`checkpoint_headers.py` 为只读 SSH 采集脚本；`checkpoint-headers.json` 为本轮库存。
`audit.json` 保留全部 128 步、2/4/8 组分组、矩阵形状、各层切分内存和条件敏感性。
`verify.py` 用独立组合穷举复核 155 个分组问题，检查 384 次逐步请求覆盖，
并调用实际 `reserve_owner_pages()` 核对 null page；此外检查文件头几何与流水递推。
仓库文本的来源哈希先统一 CRLF/LF，避免换平台检出造成伪差异；safetensors 文件头仍使用原始字节哈希。
这些 CPU 检查不能代替 full-head kernel、图捕获、P2P 或 NPU 正确性资格。
