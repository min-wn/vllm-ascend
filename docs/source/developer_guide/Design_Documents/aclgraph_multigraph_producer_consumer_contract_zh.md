# 多图提前消费的可行性：数据就绪、核心进度与强基线预算

日期：2026-10-20。延续[多图研究目标](aclgraph_multigraph_research_goal_zh.md)。
本轮只读源码、复算历史 trace，并通过 SSH 读取公开 SDK 头文件与 ELF 导出；
没有启动新 NPU kernel、修改驱动或改动生产推理路径。

## 1. 当前判断

**“保留一次大 GEMM，让就绪请求提前向后推进”仍值得从机制上分析，
但尚未形成可直接深入实施、可信地大幅超过同等优化 Padding 的多图方案。**

本轮补齐三项此前不够具体的约束：

1. 核查的公开 A2 small-M Down/ReduceScatter 源码按隐藏维度的**列带**推进通信。
   下一层 RMSNorm 需要完整隐藏行；内部列带进度不等于完整请求就绪。
2. 该公开路径请求混合核资源、设置 batch 调度并使用核间同步。
   即使增加输出标志，也不能直接假设另一张图获得并发执行资源。
3. 若先等完整普通 Down 结束，再重叠逐行归约与下一层投影，就会放弃部分现有融合收益。
   在固定旧 profile 成本的条件模型中，即使无限细分且零附加成本，
   该边界相对融合 Padding 的算子清单差值也只有约 **59～63 μs**。

第三项是跨模式 profile 数值的条件算术，**不是测得的加速率、通用性能上界或硬件预测**。
它改变当前决策：不以“能隐藏约 170 μs 投影”为理由，立刻实现大规模 row-ready 多图。
需要同时保住融合生产者的收益，并证明数据与核心确实允许下游推进。

## 2. 三个必须分别成立的条件

对一个请求行块，定义三种时间：

| 时间 | 需要证明的事实 | 不能使用的替代证据 |
| --- | --- | --- |
| 数据就绪 | 所有 rank 的必要归约、完整隐藏列、残差与 Norm 已完成并可见 | 某个 GEMM tile 完成或某段通信开始 |
| 可以执行 | 消费者具备执行资源，生产者仍保证前进 | 不同 stream、配额或不同 graph handle |
| 缩短端点 | 提前执行减少完整 step，足以支付碎片化、整理、提交与 join | 两个 kernel 在 trace 上出现重叠 |

多图只能增加调度选择，不能自动建立这三个条件。
固定选择仍须与相同 kernel、地址、流和依赖的组合单图比较。

## 3. 公开 Down/RS：为什么内部流水还不够

### 3.1 固定源码与安装二进制的边界

本地参考仓库固定到以下 revision；审计从 Git 对象读取文件，避免 Windows 换行影响哈希。

| 仓库 | 固定 revision | 本轮用途 |
| --- | --- | --- |
| [CANN ops-transformer](https://gitcode.com/cann/ops-transformer) | `b58ac682305ab2ddc753dccde4111acab8bd6af5` | A2 Down/RS 的 tiling、通信分块和资源请求 |
| [CATCCOS](https://gitcode.com/cann/catccos) | `4359f7fb80decb4a83236f41af5dea980232acc5` | 算子内部信号、通信分组和 host wrapper |
| SHMEM，以上仓库的 gitlink | `aa1e4c24f706a4f9d63975c77e527ef1eb37ca9f` | 配套要求与设备同步约束 |
| CATLASS，以上仓库的 gitlink | `db93081ce9b0ad6c04e99b9ed5f2fba081ccdb00` | 有界跨核信号协议 |

**这些是当前公开源码，不是已建立编译关联的安装包源码。**
下面的算法选择与资源请求只能作为接口设计约束和候选解释，不能写成本机已观测的内部 tiling。

### 3.2 small-M 的选择与输出就绪维度

`mc2/matmul_reduce_scatter_v2/op_host/op_tiling/arch22/`
`matmul_reduce_scatter_v2_aiv_mode_tiling.cpp` 的 642～653 行中，
非 910C、非量化、`M<=2048`、`N>512` 且输出少于 180 MiB 的情况选择 small-M。
假设 BF16 A2 的 `M=304/400`、`N=5120`，满足这份源码的条件。
这没有证明安装二进制在历史实验中选择了同一实现。

`op_kernel/matmul_reduce_scatter_aiv_mode_smallM.h` 中：

- 403～426 行按 `n_st:n_ed` 的列带等待 GEMM、同步并向对端发布阶段标志。
- 440～515 行按同一列带远程读取各 rank 的部分结果，累加到 rank 所属行的对应隐藏列。
- 527～561 行构造 `CommColumnSplitter` 并安排通知、远程读取与结束握手。

对隐藏行 r，下一层 Norm 所需的时间是：

```text
row_ready[r] = max(该行所有隐藏列完成必要归约的时间)
```

前几段列带结束时，所有行都可能仍缺最后几列。
因此，在不改变 Norm 依赖时，至少要推进到最后列带才有完整行可供消费。
最后列带内部仍可能先完成部分行；源码没有导出对应外部逐行完成接口，
本轮也没有测量这些行的具体就绪时刻。不能据此断言全部行同时完成，或硬件重叠绝对为零。

### 3.3 增加标志仍不解决核心进度

同一公开 tiling 的 1111～1114 行设置 batch 调度，注释说明涉及 `SyncAll`；
1157～1160 行根据平台 AIC/AIV 数计算 blockDim。
架构入口 `op_kernel/arch22/matmul_reduce_scatter_v2.cpp` 第 46 行声明混合核任务类型。

这些请求与内部屏障足以否决“只加 flag，另一个图就自然跑起来”的假设，
但不是实际占用率测量，也没有证明硬件不能提前释放部分资源。
任何持久消费者都必须保证未完成的生产者可以取得资源；
不能让等待者占住生产者必需的核心后自旋。

## 4. CATCCOS 和本机接口能提供什么

CATCCOS 的 `include/catccos/dgemm/kernel/matmul_reduce_scatter.hpp`
按 `commInterval` 分组 tile，Cube 侧发布内部跨核信号，Vector 侧等待后执行通信与屏障。
这说明内部细粒度流水已有公开实现；`commInterval` 调整本身不是新算法。
内部跨核信号也不是任意外部 kernel 可以等待的 ACLGraph event。

本轮核查的 `dgemm/device/device_dgemm.hpp` wrapper 在 launch 后调用
`aclrtSynchronizeStream`，不能原样进入异步捕获热路径。
库内另有其他绑定，不能把该 wrapper 的同步推广为所有路径都同步。
示例显式使用 FP16、RowMajor；没有据此取得本项目 BF16/NZ、动态图重复回放的资格。

固定 SHMEM 文档中所列的 CANN 配套均使用 HDK 25.0.RC1.1，
本机只读快照为驱动 24.1.rc3，超出该文档配套组合。
这不是实测失败，也不等于证明旧驱动绝对不能运行；本轮没有安装或升级软件。
设备 barrier 文档还要求 MIX 核，并明确提示不能与 `SyncAll` 混用。
CATLASS 的跨核信号协议有最大连续深度及反向确认，不能设计无界单向通知队列。

另一方面，本机 SDK 不只有头文件声明：
本轮读取三个库的 ELF 符号表，在 `libhccl.so`、`libhcomm.so`、`libhccl_compat.so`
中找到了七个查询符号，包括通信句柄、缓冲区、对称窗口和资源上下文接口。
因此，**原生 HCCL 适配是可以继续核查的替代入口，不应因为 SHMEM 配套表就一并否决**。
但没有加载或调用这些符号，更未验证 ABI、旧驱动支持、对端地址可见性、进度和捕获安全。

相关基线接口与说明已保存在
[安装包 AG/MM 接口快照](aclgraph_agmm_installed_interface.json)。
公开 ops-transformer 也列有 A2 BF16/NZ AG/MM 配置，进一步说明该方向应当纳入公共融合基线。

## 5. 一次大 Down 后再做 row-ready：收益为什么缩小

候选 A 的结构为：

```text
一次普通完整 Down
  -> 按完整请求行归约 + 残差/Norm -> 发布行块
  -> 一个整批投影 kernel 消费这些行块
  -> 保留完整 GDN 后继、状态提交和最终汇合
```

它避免把 Down 拆小；若消费者确实只需 Cube，先完成 Down 也有助于避免
Cube 消费者阻塞未完成 Cube 生产者的问题。
但独立通信、Norm 与消费者能否并发，仍需要真实资源和可见性资格。

最大的成本变化是：它不能免费继承当前大 Down/RS 已实现的生产通信融合。
已有完整两层 B98/Q4、默认容量 400 的 trace 提供以下清单，单位 μs：

| rank | 普通 Down D | 普通归约 C | 普通两个输入投影 P | 融合 Down/RS | 外部 AG | 融合路径两个输入投影 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 0 | 204.504 | 252.745 | 170.643 | 219.504 | 126.222 | 170.424 |
| 1 | 208.360 | 248.720 | 172.480 | 225.600 | 124.860 | 169.720 |

这里只列同一边界的这些算子，不包含完整 Norm、后继、等待与其他工作。
在“固定旧 profile 时长、通信与投影无竞争、任意细行流水、忽略附加成本”的模型中：

```text
候选 A 的流体理想清单 = D + max(C, P)
融合基线清单         = fused_DownRS + AG + fused_P
两者清单差值         = 58.901 / 63.100 μs
```

这不是硬件下界：通信算法、输出顺序、kernel 质量改变后，固定成本假设就失效。
不同模式的 profile 还可能受剖析、rank 到达和频率差异影响，不能将这个差值报告为实测加速。
它只说明：**完整隐藏 P 的乐观设想，仍需支付放弃现有融合的差额**。
不能把约 170 μs 直接拿作净收益预算，或跨层相乘预测完整模型收益。

### 有限分组还有流水尾部

让第 i 组包含 `m_i` 行。进一步假设通信和投影都严格按行数线性缩放：

```text
R_i = C * sum(m_1..m_i) / M
E_i = max(E_(i-1), R_i) + P * m_i / M
候选清单 = D + E_last
```

审计只在原默认容量表内选组，要求每组能容纳 TP2 下完整 Q4 请求，总容量保持 400；
没有新增 capture size。动态规划计算该理想模型的单 rank 最优划分，
再将两个 rank 提案放到两个 rank 上共同评估，采用相同分组顺序。
后一步只是这组提案中的选择，不宣称求得了跨 rank 全局最优。

| 分组数 | 选定的共同容量顺序 | 模型候选清单，取较慢 rank | 相对较慢 rank 融合清单 520.180 μs 的差值 |
| --- | --- | ---: | ---: |
| 1 | 400 | 629.560 | −109.380 |
| 2 | 232+168 | 529.522 | −9.342 |
| 4 | 152+112+80+56 | 481.227 | +38.953 |
| 8 | 128+88+64+40+32+24+16+8 | 462.854 | +57.326 |

单 rank 两组最优也分别比各自融合清单差约 10.645、9.342 μs。
因此，在该固定成本线性模型内，双图 row-ready 连乐观清单门槛都没过。
四组、八组也只有几十微秒余额，真实的额外提交、同步、Norm、权重复用损失会消耗它。
模型将两个必要输入投影合成一个连续服务时间，已经放松了真实多投影的约束。
这不是建议创建八张图；把这些模型组实现成单 kernel 内任务，也仍需与组合单图比较。

这些数字只否决**该模型下的“完整普通 Down 后再重叠”大收益解释**，
不否决保留融合生产者、改变通信算法或其他跨边界算法。

## 6. 另一条候选：按列消费并延后 RMS 缩放

为顺应列带就绪，可以研究先做未归一化投影，最后补每行 RMS 标量。
对完整归约并加好 residual 的行 z：

```text
a = rsqrt(eps + sum_j(z_j * z_j) / H)
U = sum_j((z_j * gamma_j) W_j)
Y = a * U + bias
```

这是实数代数等式，不能把 BF16 中间舍入、累加次序改变后的结果视作逐位相同。
必须保留实际 eps；bias 在缩放后处理；每个必要投影都要得到修正，
不能在 SiLU、门控、卷积等非线性之后才补一个通用标量。
当前 GDN 的 QKVZ 与 BA 两个输入投影均包含在工作清单中。
gamma 可以在读激活时应用，不要求再复制一份模型权重。

两个容易遗漏的依赖是：

1. 列分段会将下一投影的 K 维拆开。多个部分输出需要正确累加，
   可能增加 HBM 往返和小 K 低效，不能把相同 FLOPs 当成相同时间。
2. ReduceScatter 之后，每个 rank 只持有其所属请求行。
   后继仍使用原输出维 TP 权重切片时，要为所有请求产生本 rank 的投影结果，
   仍需要隐藏数据的 AllGather 或经过证明的其他分布式变换。
   **不能因为局部列带可用，就省掉跨 rank 数据恢复或 residual 恢复。**

此外，公开混合融合核的资源问题仍然存在。
改变 RMS 的数据依赖，并不会自动使另一个外部消费者取得核心。

[FlashNorm](https://arxiv.org/html/2407.09577v5) 已研究将归一化标量延后到线性层输出，
因此这条代数变换属于可借鉴的公共优化，不是本项目独立多图的新颖性。
本项目若继续，只能研究这些真实 TP/状态/就绪约束下尚未解决的具体调度问题，
并给 Padding 相同能力。当前没有选择它作为已成立的主线。

## 7. 与相关工作的实际区别

| 工作 | 已有内容 | 本轮不能重复宣称的贡献 | 仍需本项目证明的内容 |
| --- | --- | --- | --- |
| [TokenWeave](https://arxiv.org/html/2505.11329v2) | wave-aware token split、归一化重排、低资源通算融合 | 双批通信重叠、RS/Norm/AG 重排 | 默认小容量 A2、真实状态与旧驱动约束下是否有剩余净收益 |
| [FlashOverlap](https://arxiv.org/html/2504.19519v2) | GEMM 完成信号、输出重排、通信波次组织 | 在 GEMM epilogue 发信号这一宽泛想法 | 完整请求行就绪、A2 资源进度及动态图组合的额外价值 |
| [FlashNorm](https://arxiv.org/html/2407.09577v5) | 延后 RMS 标量与相关融合 | 将 Norm 移到投影后缩放 | 保留 TP 数据归属、残差和有限精度语义后的实际关键路径 |
| CANN Down/RS、AG/MM 与 CATCCOS | 算子内部流水、通信分组和同步 | 内部通算并行本身 | 外部行块接口、跨图生命周期和同等强基线下的净收益 |

外部 GPU 工作不构成本机证据；例如 FlashOverlap 当前公开说明要求规则 M/N 边界，
不能把其代码直接当作默认 304/400 容量已通过的实现。
上述区别是研究定位，不是已经证明本项目具有原创算法。

## 8. 完整执行协议与下一项准入

若保留融合生产者的 row-ready 候选继续分析，至少需要以下完整协议：

1. 回放前确定所有 rank 一致的计划：step 代次、完整请求行范围、TP 输出归属、
   kernel 模块、缓冲槽和通信序号。真实长度、页表与 FIA update 仍提交并计时。
2. 生产者写入本代数据；只有全部必要归约、残差与 Norm 完成并具备消费者可见性后，
   才发布对应行块。列带进度和完整行进度分开表达。
3. 消费者按合法行块处理，在一次大投影内部保持权重复用；
   调度必须保证生产通信与消费者均前进，不允许依赖 stream quota 假定独占核心。
4. TP collective 使用跨 rank 一致的顺序。若按就绪情况决定次序，必须预先达成一致，
   本地先就绪不能直接改写 HCCL 顺序。对等窗口方案也必须证明双方的 epoch/ack 协议。
5. KV 写入、GDN 状态事务、完整 hidden/residual 恢复及状态 commit 全部闭合；
   读者确认完成前不能复用缓冲。图池仅按已证明的并发安全规则使用。
6. 所有必需结果和状态完成后才停止计时；失效计划在提交前回退，
   已有图等待某代事件时不能临时改走 Padding 留下悬挂等待。

先通过以下门槛，才安排深入 kernel 或全模型改造：

| 顺序 | 最小工作 | 通过条件 | 未通过后的动作 |
| --- | --- | --- | --- |
| 1 | 保留现有融合收益，画出一个具体边界的生产/消费与核心分配 | 完整行可用、通信次序、可见性与资源进度都有明确实现入口 | 不实现只有 flag 的多图 wrapper |
| 2 | 在完整工作清单上预算多个边界的窗口并集 | 扣除失去的公共融合、必要数据恢复和消费成本后，仍有值得验证的完整 step 余额 | 否决该具体路线，继续寻找不同机制 |
| 3 | 必要时只做一个协议资格 probe | 无额外权重副本；换代、图重复回放、双 rank 进度及状态端点正确 | 不扩大性能矩阵 |
| 4 | 一个闭合段的四对照 | 同等 Padding、多图串行、多图并行、等价组合单图；完整端点净胜 | 没有净胜则不建立动态路由器 |

若等价组合单图达到相同表现，贡献先归为依赖调度或算子接口。
只有在有用选择随动态状态改变、实际捕获预算限制组合目录，且模块复用的额外开销可支付时，
才能继续主张独立多图的适应性价值；这与并行执行收益分别验证。

**本轮结论仍是机制审查进展，目标保持进行中。**
没有因文档和审计通过，就宣称已经找到大幅多图净收益方案。
