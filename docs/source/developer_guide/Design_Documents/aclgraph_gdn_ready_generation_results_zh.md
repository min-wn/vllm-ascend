# GDN 请求组 ready：离线真实自回归生成结果

> 状态更新（2026-10-22）：当前compact Q1/Q4部署扩展已正式结束。本文是历史阶段记录，旧候选资格、runner接入及补救建议不再是待办；数值、性能和失败数据保持原样。当前边界见[最终收口结论](aclgraph_gdn_compact_closeout_zh.md)。

本轮结论：**真实生成循环存在符合冻结标准的稳定收益，值得规划实际 runner 接入；完整批次收益须单独判断。** 生成循环均值耗时改善为 **+2.669%**，包含 prefill、一次导入、终末提交的批次阶段合计改善为 **+1.373%**。这些是同一 compact 算法的调度对照，不是官方与 compact 的质量评测，不是在线服务吞吐。

完整批次三对分别为 -2.882%、+2.475%、+4.314%，**尚未证明包含 prefill 的完整批次稳定净收益**。生成循环三对均改善，不能覆盖这一限制。

## 冻结对象与实际执行

保持 Qwen3.5-27B TP2、compact FP32 状态与原 BF16 head，HF32 关闭、FP32 matmul highest、304 个原 NZ29 decoder 投影、20 AIC/40 AIV 与原内核库不变。模型权重不变；设备为 910B3 的卡 0、1，软件、拓扑可见信息与环境记录见本轮证据。上一轮 beta/gate 复用候选没有使用。本轮仅有 allocator 的显式 owner 数参数与离线 Python 适配入口，未修改 recurrence 算术、ABI、槽数或 ready 协议。

固定 56 个请求，四条已有自然语言 prompt 各 14 次。chat template 关闭 thinking，greedy，正常 EOS，输出上限 256 token，prompt 长度 33..37。冻结后 workload SHA 为 `520c70cd7415449c2e8b53b78b8492a1e130b1c544d5a31a6bb3f3c35cb73181`。每 owner 预留 prompt+256+4 个逻辑 token，最大为 297，实际所有 FIA 访问均经原页表边界检查。原上下文上限仍为 2048。

捕获所有可能 live B1..56 在本机默认 dispatcher 下的 29 个容量，范围 4..224；没有新增 size 或路由器。实际生成有 239 个 Q4 验证步，live batch 最小/均值/最大为 9/40.201/56，实际容量及出现次数见 `workload-and-cost-breakdown.json`。这是从中负载起步并随真实 EOS 缩小的有限批次，不能称为持续 B56。

六个独立 TP2 进程组全部正常结束。三对顺序为 delayed→ready、ready→delayed、delayed→ready；每进程先独立零态真实 prefill，再用自身合法快照运行验证轮和计时轮。没有给另一侧注入 hidden、状态、token 或预定接受长度。

所有进程输出均为 **10026 token**，其中 prefill 给出 56 个首 token，生成循环实际输出 **9970 token**。46 个请求正常 EOS，10 个触及长度上限，长度范围 101..256。EOS 计入输出；未输出的 Q4 候选不计吞吐。真实 ngram 共提出 2691 个 token，接受匹配数按原 bookkeeping 记录为 362；接受长度直方图见证据，未预设每步接受数。

实际接受长度 1/2/3/4 分别出现 9416/79/56/57 次，总计 9608 次请求验证，平均实际输出约 1.038 token/请求验证。ngram 在这批真实文本上的帮助很有限，仍完整执行，没有将低接受请求剔除或改为固定接受。

## 完整成本与吞吐

单位秒。每组选择阶段合计最大的 TP rank，使用该 rank 的四列相加，表为三个独立进程的均值。没有把不同 rank 的最大分项相加。prefill 包含真实模型前向、首个 BF16 head、预测与首 token 回传；导入包含一次 compact 激活和 workspace 保留；生成包括实际 draft、host/NPU 交互、图更新、模型、head、TP、接受与提交及等待；终末为最后真实接受前缀物化与完成等待。

| delayed | 23.139986 | 0.091166 | 21.325973 | 0.009469 | 44.566593 |

批次合计剔除了捕获、验证、snapshot/restore 间隔，是四个真实阶段的成本之和，**不是连续 wall-clock 请求延迟**。新进程 prefill 没有额外人为预热；生成循环经过自身验证轮预热。模型加载、缓存分配与捕获另外记录，不混入生成性能。

## 新增闭环成本与解释边界

以下是相同 critical rank 的三个进程均值；单位秒，百分比相对各自生成循环。它们是 host 阶段边界，包含必要同步，不能当作每个设备 kernel 的独占成本。

| 阶段 | delayed 秒 | ready 秒 | delayed 占比 | ready 占比 |
| --- | ---: | ---: | ---: | ---: |
| 真实 ngram draft/输入构造 | 0.405947 | 0.409747 | 1.90% | 1.97% |
| host 状态准备、metadata/token 上传及图任务准备 | 1.269079 | 1.295788 | 5.95% | 6.24% |
| 图 replay/update、模型/head/TP/提交及完成等待 | 19.446006 | 18.834400 | 91.18% | 90.74% |
| argmax、TP broadcast、实际 token 回传 | 0.156136 | 0.168164 | 0.73% | 0.81% |
| 真实接受判断/请求推进 | 0.043185 | 0.043063 | 0.20% | 0.21% |

这些阶段的和与循环总耗时之间还存在轻量 ledger、active 列表及计时本身的共同开销，全部留在循环分母中。逐步 token、draft、接受与终止记录先写内存，JSON 在计时结束后落盘。详细 hidden/状态下载、有限性扫描和哈希只在验证轮或计时结束后执行。正式算法所需 argmax、broadcast 和 D2H 没有移除。

图 replay/update 与等待包含 decoder、FIA 长度更新、BF16 head、TP、deferred commit 等共同成本，本轮没有把其差值独占归因给 GDN。prefill 时 compact 调度尚未安装，两种调度走相同原 prefill；它的进程间差异是本批次实测事实，不能称为 ready 算法导致的改善或退化。短请求的四阶段合计尤其容易受它稀释或波动影响。

本轮生成循环平均节省约 0.569 秒，replay/update/wait 边界约减少 0.612 秒，其他 host 阶段合计增加约 0.043 秒。由此只能定位到图内执行及等待这个组合边界，不能把 0.612 秒解释成独占 kernel 节省。delayed 中 draft 约 1.90%、metadata/token 准备约 5.95%、预测回传约 0.73%、接受推进约 0.20%；新增 CPU draft 并没有占据闭环大部分时间。prefill 约占整个批次一半，并有明显进程间波动，足以影响只有约半秒的生成收益。

旧含 BF16 head 的固定轨迹中负载回放约 3.13%、原 Q4 轨迹约 4.55% 的结果继续保留；本轮 token、接受和结束来自真实生成，负载会收缩、KV 范围和步数也不同，不能把与旧数字的差额全部解释成 draft 开销。它们属于不同工作负载、不同边界的独立证据。

## 正确性、去留与归档

同算法 delayed/ready 在各 TP rank 的初态、每步 hidden 字节、完整生成 token、draft、预测、接受长度、owner/位置/bucket、结束原因，以及终末 compact/卷积/FIA 状态一致。每个正式轮也与自身不计时验证轮一致，全部最终日志债务清零，零 fallback。跨进程重复同样执行相同工作量；所有失败/截断样本均保留。

逐步 hidden 摘要来自不计时验证轮；正式轮核对完整生成 ledger 与终末状态，不在正式循环中下载 hidden 或状态。这样保留生成所需同步，同时避免将详细审计加入生成时延。

这些检查仅验证同一算法调度，不覆盖原官方数值与任务质量失败，不能宣布部署资格。本轮没有 AIME、首次分歧、FP32 head、官方比较、新内核或参数搜索。

## 后续 runner 接入计划的边界

生成循环通过本轮判据，足以进入接入设计，不足以承诺服务收益。本轮只记录以下计划，没有实施新的 runner 或启动额外测量：

1. 在现有 runner 的真实 prefill→decode 过渡点复用一次 compact 导入，保留当前 owner/四候选映射和 request-finished 的最后接受态提交。先明确生产 runner 的 KV block 与 owner 生命周期如何映射；若需要改变状态 ABI 或 recurrence，先报告具体缺口。
2. 复用 runner 当前默认 dispatcher、真实 FIA graph update 和 ngram 接受结果，只暴露 delayed/ready 调度切换。保持原 BF16 head 和全部核资源，不新增路由器，也不改 draft/采样策略。
3. 首个接入验收仍使用这一份冻结短文本，独立检查两种调度 token/draft/接受/终止和完整状态一致，再测包含服务所需 host 工作的生成边界。prefill 的首次使用成本、预热状态与捕获必须独立记录；不能用本轮正的批次均值宣称完整请求收益已经成立。

目前没有发现足以支持另一个内核修改的独占成本，本轮不提出或启动新的内核候选。优先保持约 2.67% 已观察生成收益在实际 runner 中不被接入开销吞掉。
