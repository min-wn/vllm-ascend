# 融合 Down 接入完整相邻两层：结果与方案调整

日期：2026-10-20。

**结论：公共融合在两层内仍有收益，但“融合后再按请求切成两份”没有超过同等融合的 Padding。**
三轮中融合 Padding 的设备时间改善 2.14%～2.62%；融合切分反而比融合 Padding 慢 2.29%～2.46%。
因此不把当前融合切分结构扩大到完整模型。下一步先核查保留大矩阵、改变请求行归属的可行性。

## 1. 实验实际覆盖什么

- 机器：现有双卡 910B3，驱动、镜像均未修改。
- 模型段：Qwen3.5-27B TP2 的完整第 3 层 FIA → 完整第 4 层 GDN。
- 入口 hidden/residual 和 KV 前缀是受控合成数据；使用真实模型权重及真实层代码。
- B98、每请求 Q4，392 个有效 token；默认捕获容量为 400，切分为 200+200。
- 400 和 200 均来自默认容量表，没有为切分增加专用图容量；每个请求的四行保持完整。
- 所有模式均计入 FIA 的真实 host 长度更新、元数据 H2D、状态提交和最终流汇合。
- 切分模式在下一层输入投影之后、状态 core 之前合批；采用相同 packed 合并优化，保持一次 core 和一次状态提交。

这不是完整模型、生成质量或服务吞吐测试。此前完整模型约 0.165% 的设备均值改善仍是独立历史结果，
不能用本轮两层收益替换，也不能把两层收益按层数线性放大。

执行方式补充：每个 mode 捕获一张图，切分和多流依赖在图内实现，各 mode 依次计时。
本轮并非多张图独立并行 replay 的对照，不支持多图独有收益结论。
后续按 [多图主线与公共融合辅线](aclgraph_multigraph_exclusive_plan_zh.md) 分别推进。

## 2. 公平对照与计时

本轮同时运行六组：普通 Padding、普通切分等待全部、普通切分提前消费，以及三者对应的融合版本。
融合使用已有 `npu_mm_reduce_scatter_base(..., comm_mode="aiv")`，再用 AllGather 恢复输出。
Padding 只执行一次容量 400 的融合算子；切分执行两次容量 200 的融合算子。
切分的提前消费组与等待组有相同算子和工作量，仅改变下一层输入投影的启动依赖。

三轮各六个计时样本，轮间正反交替模式顺序。每次恢复相同的完整初始状态；
原始双 rank 样本均保存，先逐样本取慢 rank，再计算各轮中位数。
下表为无 profiler 的设备时间，单位 μs；百分比按时间减少计算。

最终仍多花 86.48、92.97、89.84 μs。

## 3. Profiling 定位到的损失

以下是两张卡各自的 trace 范围，用于结构归因，不能与无 profiler 计时直接相加。

| 项目 | 融合 Padding | 融合提前切分 | 解释 |
| --- | ---: | ---: | --- |
| 融合 Down kernel 累计 | 219.5～225.6 μs | 323.2～330.7 μs | 两次小融合比一次大融合多 97.6～111.2 μs |
| 下一层输入投影累计 | 169.7～170.4 μs | 245.2～248.7 μs | 拆小仍多 74.8～78.9 μs |
| AllGather 累计 | 124.9～126.2 μs | 146.6～147.5 μs | 两次通信总工作增加 |
| A 段投影覆盖末次 AllGather | 0 | 48.6～48.8 μs | 普通切分对应窗口约 118～119 μs |
| Down 起点至下一层 O 投影起点 | 1020.4～1022.1 μs | 1130.8～1142.4 μs | 闭合边界慢约 110～120 μs |

切分的第二次融合 Down 还能覆盖第一次 AllGather 约 72～73 μs，但这已经包含在完整调度结果中，
不能再额外加成。融合路径减少了后续可覆盖的通信窗口，同时仍承担 Down 与输入投影的拆小成本。

十二份 trace 核对算子数量和依赖：融合 Padding 有一次融合 Down、一次 AllGather；
融合切分各有两次。两者均只有一次 FIA、一次 GDN solve、一次状态提交。
输入投影必须等待自身行的 AllGather，core 必须等待所有投影；等待组还必须等待全部行。
这些检查排除了漏算状态工作或读取未完成输出造成的虚假收益。

当前 trace 看不到融合 kernel 内部各块的完成事件，不能证明内部具体是哪种资源争用，
也不能仅凭累计时间把损失全部归为 AIV 争用。可以确认的是：现有接口下，两次融合加小投影的结构不划算。

## 4. 数值与正确性证据

连续资格检查使用 live batch 98、97、99，状态跨步延续。每个 rank 的六模式共十八项检查通过：
各模式 eager 与 graph replay 的输出及完整状态一致，inactive/null 状态一致；
相同算法的提前消费与等待全部输出、状态一致。普通 Padding 与官方完整两层调用一致。

相对普通 Padding，融合 Padding 的 hidden NRMSE 约 0.255%～0.295%，
residual 约 0.0836%～0.0877%；融合提前切分分别约 0.262%～0.296% 和 0.0846%～0.0934%。
所有已记录的 hidden/residual 元素均满足本轮诊断阈值 `abs(error) <= 0.02 + 0.02 * abs(reference)`。
这反映融合改变计算路径后的局部数值差异，不等于完整模型精度认证。

本轮没有量化融合算法与普通 Padding 之间的完整状态漂移，也没有 logits 或长生成质量结果。
“同一算法 eager/replay 完整状态一致”不能替代这些检查；若后续进入全模型，必须补上。

## 5. 与已有工作、毕业设计贡献的界限

GEMM/ReduceScatter 融合来自已有 torch_npu 接口，仓库已有对应融合 pass；它是公共能力，
本轮 2.14%～2.62% 的两层收益不能写成原创切分方法的收益。
本轮新增证据是：在当前驱动和 ACLGraph 下接入真实相邻层，公平开放融合能力后，
原先的切分提前消费优势不足以补偿新基线下的拆分成本。

切分仍独有的自由度是让完整请求子集提前拥有可用数据、启动后继工作。
但实现必须同时避免把高效的大矩阵拆成低效小矩阵；“有重叠”本身不是贡献成立的充分条件。
此次结果对论文的作用是明确失败条件、强化基线和收紧设计目标，不能包装为正向端到端加速。

## 6. 调整后的下一步：先审查数据归属，再决定是否实验

暂停扩大当前“两次融合 Down”的方案。候选结构是：

1. 保留一次全容量融合 Down/ReduceScatter，让每个 TP rank 持有完整请求的部分行。
2. residual 按相同请求行取本地视图，在本地完成逐行 Norm。
3. 核查 AllGather/Matmul 是否支持把请求行恢复和下一层投影流水化，保留足够大的计算块。
4. 在 GDN core 前恢复正确的全请求顺序，状态归属、inactive 行、残差输出与最终汇合全部闭合。

这尚是候选方案，不是已验证优化。必须先回答：本机接口是否支持当前 BF16/NZ、图捕获及目标投影形状；
行归属是否跨整请求边界；Norm 返回的 residual 需要怎样恢复；额外通信和拷贝是否抵消所省的等待。
如果需要更换权重布局、重复权重或增加独立的小 GEMM，应把成本明确计入，而不能宣称保留大矩阵效率。
不能读取普通融合算子尚未完成的部分输出。

进入小实验前的门槛是画出完整依赖和通信量，确认相对本轮融合 Padding 确实删除了等待或搬运，
且没有重新引入两个小 Down。若接口无法满足，就否决此候选；不再通过扩大测试矩阵寻找偶然收益。
该结构与序列并行及通算融合有关，不能预先宣称原创；可研究增量仍需落在动态请求、图容量与状态归属的联合处理。
