# 固定 ACLGraph 消费动态描述符：候选比较与最小方案

日期：2026-10-20。按[最新目标](aclgraph_multigraph_research_goal_zh.md)，
不再要求独立多图独有收益，不增加路由器，不扩完整模型。
历史切分负结果用于控制成本；组合单图或 Padding 可复用算子不构成否决理由。

## 1. 当前选择

**已选 attention 的共享计划生成器，完成具体原型与最小验证；当前原型没有净收益，停止扩大。**
研究固定网格 AIV 算子，直接读取设备端真实 KV 长度，
生成同一份 1024 个 int32 原生元数据，替代当前 AICPU 生产过程。

七代输入的全部导出字、固定地址和描述符不变性通过。
补齐计时后检查的正式端点中，AICPU 为 126.29 μs，AIV 为 199.25 μs，后者慢 57.77%。
这是包含必要长度上传的生产者端点，未测 attention 计算或模型收益。
因此没有接小规模闭合 attention 链，也没有增加路由器或扩完整模型。
这是一项有预算依据的局部选择，不是大的性能收益承诺。
共享计划每步只执行一次，不能乘以 attention 层数。

## 2. 三候选成本账本

复用原始 128 步动态轨迹、Q4、原默认容量表，没有新增专用容量。

| 候选 | 已核算的成本 | 不能直接当作可消除成本的部分 | 决定 |
| --- | --- | --- | --- |
| 动态 dense | 有效行 49972，物理行 50688；无效行 716，占 1.41256% | 16/32/64/128 行分块下，动态有效行与容量的总块数完全相同 | 保留社区对照，不新写 GEMM |
| 动态 attention | 原共享完整头计划的 AICPU profile 为 69.12～118.10 μs/步，另有必要元数据清零 | consumer 本来就按真实长度执行；不能重复计算旧 host update 收益或全部 padding 工作 | 选共享计划生产者 |
| 动态通算融合 | 已融合 Down/RS 为 219.50/225.60 μs，完整行恢复 AG 为 126.22/124.86 μs，分别为两 rank | 必要归约、行恢复和 residual 不会自动消失；已隐藏的工作不能再算一次 | 暂不做新融合核 |

行数、块数与不同历史 profile 的时间不能相加或推算整网百分比。
分块结果只是指定 tile 的整数几何，不代表安装版 dense 一定使用这些 tile。
attention 时间取历史诊断 `whole` 路径的全部记录；profile 有扰动，
新算子仍须在同进程、无 profiler 端点比较。

### 2.1 社区动态 GMM 的最小结果

本机 `npu_grouped_matmul` 的 Tensor 重载接收设备 `group_list`。
[固定版本官方文档](https://gitcode.com/cann/ops-transformer/blob/b58ac682305ab2ddc753dccde4111acab8bd6af5/gmm/grouped_matmul/docs/aclnnGroupedMatmulV3.md)
已描述有效输出范围与未覆盖区域不更新。因此“设备有效 M”不是本项目发明。

本轮单卡 910B3、BF16 合成 Down，物理形状固定为
`[400,8704] × [8704,5120]`。
同一动态图在 392、400、4、0、396、388、392 行间切换，
有效结果、精确零尾部、固定地址和计时后结果检查均通过。
小行数只用于正确性；计时只用 B98/Q4 的 392 行与默认容量 400。

四轮交替顺序，120 个计时，设备端点中位数如下：

| 对照 | μs | 端点工作 |
| --- | ---: | --- |
| NZ Matmul Padding | 234.17 | 输入更新、400 行矩阵乘及最终等待，输入尾部为零 |
| 社区完整容量 GMM | 214.74 | 相同输入更新、400 行 GMM 及最终等待 |
| 社区动态 GMM 完整输出 | 259.80 | 相同输入更新、有效 M 上传、392 行 GMM、图内动态尾部清理及最终等待 |

动态端点比社区完整容量 GMM 慢 **20.98%**。
完整容量 GMM 比原 Matmul 快，说明不能只选择较弱旧基线；这部分不是动态描述符收益。
GMM 的 ND 三维权重与 Matmul 的 NZ 二维权重同时改变布局和调度，
不能将其全部差值归因于某个单独因素。

尾部清理是本探针“完整输出且无效区精确为零”的契约要求。
若后继直接消费有效域，可能不需要清零，但需验证完整消费契约。
当前结果不证明所有动态 GMM 都慢，也没有分离 H2D、比较和清理各自的因果成本。
不连续增加技巧来挽救这一小预算场景，先推进另一明确对象。

首次探针在 NZ 基线格式构造时失败：三维父张量的二维 view 保留了不适用的存储描述。
修正为独立二维 clone 后转换，在新进程完成资格和计时。
失败报告与对应源码保留；该失败不是 GMM 不兼容证据。

## 3. 具体机制：直接生成同一份共享 attention 计划

```text
本步必要描述符准备与 H2D
  → 固定图内 AIV：读真实 KV 长度、计算原成本、划分核范围、写完整元数据
  → 原 attention consumer：相同 Q/K/V、页表、长度、mask 与计算核
  → 最终等待
```

不将真实输入移到计时外，不把长度常量化，不在 CPU 提前算本步切分。
物理 batch 与地址在捕获时固定，描述符内容每步改变。
实现受限域为 A2、BF16 consumer、TND、分页 BnBsH、Q4/GQA6/KV2/D256、page128、
至多 128 个物理请求和 20 个 Cube 核、KV 长度 0..4097。
本轮设备实际验证的是 100 个物理请求、400 个 token；没有资格化其他物理容量。
这是隔离研究核，没有注册生产模型路径，也没有放宽到其他几何。

### 3.1 保持策略，改变生产过程

每个请求的两个 KV 头各是一个完整原子，不拆 FD 部分结果。
保留原 6/10 对齐整数成本代理，不引入新的近似权重。
这个成本是继承的调度模型，不是已校准的硬件时间。

原实现逐请求串行评估分组。本次尝试为：

1. 从设备长度计算每个头的原成本，建立非递减前缀和。
2. 对给定最大组成本，并行计算各起点能到达的最远终点。
3. 倍增跳转判断至多 20 组能否覆盖全部头，二分寻找同一最优成本上限。
4. 并行恢复各核终点，为剩余核预留至少一个正成本原子，
   保留零 KV 空洞、物理 padding 与全零输入的边界语义。
5. 一次覆盖写出完整 1024 字，清除无效核和所有 FD、GS1/S2 遗留字段。

并行前缀、查找、倍增与连续划分都是已有方法，不能宣称通用算法首创。
本项目待验证的增量是：在这个固定图和原生 ABI 下，
保持同一分配结果，减少共享计划的实际生产端点成本。
当前结果只证明这个受限原型能实现相同导出，尚未取得上述成本下降。

安装版 Triton 后端不支持 int32 的 `tl.gather`。
原型将查找值数值转换为 FP32，再转换回 int32；前缀加法和比较仍用整数。
受限域内最大整数不超过 `2 × 256 × 758 < 2^24`，转换没有舍入。
这不是原始张量的位重解释，也不能外推到任意大成本或任意长度。

### 3.2 生命周期和停止条件

- 描述符、页表、元数据和输出地址固定；DMA、计划和 consumer 使用真实流依赖。
- 元数据全部覆盖写出，最后消费者完成前禁止覆盖；当前只验证串行回放。
- 全字段必须与原生完整头策略一致；不能只抹掉 FD 计数冒充合法新计划。
- 若生产者已经没有净收益，不增加路由器或扩完整模型。
- 若生产者更快，但共享 attention 链没有净收益，同样停止扩大。
- 只有受限域内取得正确性和收益，才讨论其他形状；不存在未经验证的运行时自动回退。

## 4. 最小验证结果

CPU 模型已将前缀查找、倍增和边界恢复，与原串行完整头划分比较。
16221 个小整数成本/核数组合通过，包含零成本空洞、全零及单正原子。
原轨迹选取容量 400 的两次真实长度，增加全零、单正请求、长度边界空洞、
全部有效和恢复输入，生成七代完整 1024 字 oracle。

### 4.1 固定图资格与公平端点

设备探针使用同一进程的两张互斥固定图，分别捕获 AICPU 与 AIV 生产者；
执行时依次回放，没有并发或资源隔离优势。
同一份设备 KV 长度、同样的物理 Q4 段、固定缓冲、相同更新和等待规则。
七代输入均通过全部 1024 字与 CPU oracle、已资格化原生完整头实现的精确比较，
同时检查输入内容未改写、描述符和元数据地址未变化。

计时仅交替使用原轨迹的两代长度，不把全零/单请求边界当性能样本。
每次计时都在 host 准备本步长度，必要 H2D 和图 replay 后等待。
设备事件记录 H2D、生产者及其流依赖；wall 另外包含 host 准备、提交和最终同步。
这里的设备端点不是纯 kernel 指令时间。

每次运行四轮，顺序交替，每模式每轮 10 个正式样本，合计 80 个。
v4 是首次通过正确基线的结果；v5 只补计时后全字段检查，算法不变。
两份报告均保留，没有挑最快的一轮或一份。

| 运行 | AICPU 设备中位数/μs | AIV 设备中位数/μs | AIV 退化 | AICPU wall/μs | AIV wall/μs |
| --- | ---: | ---: | ---: | ---: | ---: |
| v4 | 125.42 | 199.42 | 59.00% | 319.13 | 390.97 |
| v5，补齐计时后检查 | 126.29 | 199.25 | 57.77% | 315.45 | 387.88 |

两次运行的各轮设备和 wall 中位数均退化。
v5 计时结束后，两种生产者全部 1024 字再次通过检查。
当前结果是单物理容量、两代性能输入的局部结论，没有统计置信区间或服务负载外推。

### 4.2 只做一次诊断 profiling

每种生产者各抓一次变化输入 replay，确认设备任务清单：

| 路径 | 计划相关任务 | 单次 profile 的长度 DMA/μs |
| --- | --- | ---: |
| 原生完整头 | 清零 AIV 1.50 μs + AICPU 102.58 μs | 2.54 |
| 新 AIV | `descriptor_plan` AIV 304.15 μs，无单独清零 | 2.36 |

profile 对新核扰动很大，304.15 μs 不能替换无 profiler 的 199.25 μs，
也不能将这些核时长与另一条运行的事件端点相减。
它说明在这条已抓取时间线上，新核内部仍是主要工作，节省一个清零核远远不够。
`NOTIFY_WAIT` 是等待这些工作的依赖，不能再加一次当作额外可消除预算。

多轮 limit 二分、向量 upper_bound 和依赖 gather 是明确存在的源码结构，
与昂贵计划核相符；没有指令级计数，尚不能把损失精确归因到 FP32 转换或某一条 gather。
不能仅凭这一次 profile 声称 AIV 硬件或 Triton 在所有计划问题上都不合适。

### 4.3 保留的失败记录与基线修正

首次设备编译因为 int32 gather 不支持失败，未产生可用性能数据。
之后两次精确比较失败，是探针误选旧 vendor，读取了仍带 FD 字段的旧库，
不是新核已确认的数值错误，也不是有效负性能数据。
当时两者头终点相同，但旧库非零 FD 字段违反 fresh whole 导出契约。

修正后，probe 强制校验 extension、公共 OpAPI 和 AICPU 三个 SHA256，
重新在新进程中验证，未降低任何字段检查。
正确 AICPU hash 为 `1c4ab9fcf2b7d2935be3e60f2a215fb65dc85859bc6fe99fe5271b4c4784ea90`；
误用旧库 hash 为 `46bafeb84baa095b84063a2d0c262f04aef1fd5d8ba51b975ca7d44a618078f2`。
报告、对应源码、实际加载的 OpAPI 路径和失败字段保留供复查。

### 4.4 本阶段判断与下一门槛

**这版“保留精确 minimax、改用 AIV 前缀查找和倍增”的实现不值得继续接 consumer。**
本阶段已完成候选筛选、具体机制和最小验证；没有完成正收益目标。
动态 dense 在当前完整输出契约下也为负；通算融合仍缺少新的可删除工作证据。
因此不能把其中一个包装成已找到可靠加速路线。

后续仍可把 attention 共享计划作为对象，但必须先改变规划成本，
而非仅更换执行单元或增加 stream。
一个可继续分析的机制是：将多轮精确 minimax 搜索改为固定工作量的设备前缀边界构造，
仍保留完整头、不拆 FD，并对正成本覆盖、严格前进、最大核负载给出约束。
这会改变分配结果，不能继续借用“与旧计划逐字相同”证明其合理。
先用已有轨迹核算负载失衡；只有新的生产者门槛通过，才接相同数据的小 consumer 链，
验证计划节省是否被 attention 尾核拖延抵消。此项尚未实现或验证，不承诺收益。

该链仍须保留“每步一次计划、16 次消费”的强基线；
不能以每层重算的弱基线、隐藏上传、预计算本步计划或完整模型扩展掩盖本轮负结果。

## 5. 与已有工作的区别

| 已有工作 | 已有机制 | 本项目待验证的增量 |
| --- | --- | --- |
| 官方 FIA sink，加本分支前阶段完整头策略 | 官方已有设备长度/AICPU 元数据；本分支已有共享、完整头 ownership 与原生 ABI 适配 | 受限 AIV 实现取得相同导出；本轮未取得成本下降 |
| [FlashInfer](https://arxiv.org/abs/2501.01005) | 计划/执行分离及图执行适配 | A2 当前 ABI 和共享生产者成本的改进，不能声称首创 plan/run |
| [官方 compressor_metadata RFC](https://github.com/vllm-project/vllm-ascend/issues/11079)与[实现 PR](https://github.com/vllm-project/vllm-ascend/pull/10741) | 固定缓冲、动态设备描述符、AscendC 生成压缩元数据 | 此处为 Q4 FIA 完整头分核，计算和输出不同；不能声称首创 AIV 元数据 |
| 社区 GMM | 设备 group_list 限定有效行和输出范围 | 本轮只有资格与成本筛选，没有新的 dense 算法 |
| CANN 通算融合、AutoOverlap/mKernel | 分块依赖、通信流水和资源分工 | 未来若推进，应证明动态描述符的额外净增量，不能将通用流水当原创 |

这是已核查范围内的区别，不是全面的新颖性证明。
毕业设计贡献需由最终代码差异与公平实验支撑，不由方案名称决定。
本轮对照是本分支已资格化的完整头生产者，不是未经修改的官方全功能 FIA。
它采用更强的跨层共享，但也限定了几何、策略和 ABI，不能据此声称全面优于社区实现。
现阶段能交付的是可复核的成本筛选和原型负结果，尚不能主张新的高性能注意力算法。
